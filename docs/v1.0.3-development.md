# PackBreaker v1.0.3 研发记录：在线升级 socket 权限与版本弹窗简化

本版目标由用户提供的 NAS/Synology Compose 和 v1.0.1 升级截图确定。研发分支不改写已发布 v1.0.1/v1.0.2 Git Tag、正式 GHCR 镜像及任何真实宿主机容器。

## 用户部署条件与已确认的代码问题

用户以 `user: "0:0"` 启动，但配置了 `PUID=1026`、`PGID=100`，并显式挂载 `/var/run/docker.sock:/var/run/docker.sock`。旧版 `container_entrypoint.py` 会在启动应用前 `os.setgroups([])` 并降权至 `1026:100`，即使主进程最初以 root 启动，也会清除访问 `0660 root:docker` 之类 socket 所需的补充组。这是**代码中确认的缺陷与用户场景吻合**；用户 NAS 的真实 socket mode/GID、Docker API 响应和容器可见性尚未现场读取，不能断言这是该 NAS 错误的唯一原因。

v1.0.3 在降权前仅检查容器内 `/var/run/docker.sock`：若它确实是 Unix socket、group 同时具备读写权限，且目标 PUID 非 0、目标 PGID 与 socket GID 不同，且目标 PUID 不是 socket owner、other 不能直接读写，则仅保留 socket 数字 GID 为补充组。其他情况下仍清空补充组；不长期以 root 运行 Web，不 chmod/chown 宿主 socket，不无条件保留 root 原有的所有组。若用户命名空间拒绝加入该补充组，会回退为清空所有补充组并继续启动服务，在线升级仍失败关闭并提示连接/权限问题。

原后端把无法连接 Docker daemon 和无法 inspect 名为 `packbreaker` 的主容器混合为 `UPDATER_DOCKER_UNAVAILABLE`，UI 一律提示权限。现在独立区分缺失挂载、socket 权限不足、daemon 连接不可用、主容器不可见，使提示与实际失败阶段一致，同时保留管理员会话、CSRF、幂等键、正式 digest、预检、一致性备份和自动回滚等原有门禁。

## 界面

删除版本弹窗底部的「版本回退」整个可展开区域和对应状态、图标、样式。**不删除升级失败后的自动回滚能力**，也不移除升级前备份与风险确认。

## 隔离验收及发布边界

- 单元测试模拟不存在/普通文件/Unix socket、`0660` 与 `0600` 权限、相同/不同数字 GID 和降权调用顺序，证明只保留 socket 组。
- 升级状态测试区分主容器检查失败与 socket 权限失败；不暴露底层 Docker 错误正文。
- GitHub Actions 的独立 Docker updater E2E 在临时容器中复现 `user 0:0`、`PUID=1026`、`PGID=100`、`no-new-privileges` 和 docker.sock 挂载，核对实际 Web 进程降权与必要补充组保留，继续执行一次性 helper/升级/回滚测试。不使用真实 NAS、PT 站点、下载器或媒体目录。

**部署限制：** v1.0.1/v1.0.2 正在运行的旧入口进程无法通过更新前端或重新挂载同一个 socket 获得新代码；如果其在线升级被本问题阻断，需在 v1.0.3 正式发布后从宿主机对已备份的 Compose 配置执行一次手动更新，再验证 Web 端下一次升级。当前 `latest` 仍以正式 GHCR 发布结果为准，研发分支不能提前宣称 v1.0.3 已上线。
