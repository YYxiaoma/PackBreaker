# PackBreaker v1.0.6 研发与发布前验收记录

## 1. 版本目标

v1.0.6 以正式发布的 v1.0.5 为升级基线，聚焦 Web 在线升级过程的可感知性，不改变现有单容器 updater、安全备份、幂等和失败自动回滚边界。

本版本目标：

1. 点击版本弹窗中的“立即升级”后直接发起升级，不再出现额外二次确认框。
2. 升级进行中，在当前版本下方持续展示进度条、阶段百分比和 helper 当前处理内容。
3. 新版本启动并通过健康状态收敛后，页面自动刷新到新版本。
4. 保留请求结果未知时复用同一 Idempotency-Key 的确认机制，禁止因为页面短暂断开重复发起升级。

## 2. 在线升级交互实现

前端版本入口继续使用现有真实 updater 状态，不增加与后端无关的虚假计时器。活动阶段映射为展示进度：

| helper phase | 展示 | 进度 |
| --- | --- | ---: |
| accepted | 已接管升级 | 8% |
| pulling | 正在拉取镜像 | 28% |
| stopping | 正在停止旧容器并备份 | 52% |
| starting | 正在启动新容器 | 72% |
| verifying | 正在执行健康检查 | 90% |
| succeeded | 升级成功 | 100% |
| rolling_back | 正在自动回滚 | 65% |

进度条下方优先展示 updater helper 返回的真实 message；没有 message 时才使用阶段中文说明。升级活动、请求结果未知或仍存在目标版本 in-flight 时，前端继续按现有短周期轮询升级状态。

自动刷新只在同时满足以下条件后触发：

- 本次页面记录了明确的目标版本；
- 服务重新可访问；
- API 返回的 current_version 已等于目标版本；
- helper phase 为 succeeded。

满足条件后显示成功提示，并自动执行页面刷新。容器切换期间的短暂 API 不可用保持静默，不把网络瞬断误判成升级失败。

## 3. 版本身份一致性

v1.0.6 将当前候选版本表面统一为 1.0.6：

- pyproject.toml
- frontend/package.json
- Dockerfile 的默认 VERSION
- uv.lock 根包版本
- OpenAPI info.version
- 后端 app_version()

源码工作区中的 app_version() 优先读取当前仓库 pyproject.toml，避免开发虚拟环境中旧 editable package metadata 导致 OpenAPI 快照或健康接口错误报告上一版本。安装包/容器环境仍保留 package metadata 路径。

正式发布基线 release-baseline.json 在 v1.0.6 正式发布完成前继续固定 v1.0.5，不提前前移。

## 8. 正式发布边界

截至本记录形成时，v1.0.6 尚未创建正式 Tag 或 GitHub Release，stable / latest 也没有前移。

正式发布必须继续由 .github/workflows/release.yml 从 v1.0.6 Tag 触发，并重新完成正式发布强门：

1. tag 与项目版本一致性；
2. v1.0.5 baseline 必须仍是 GitHub 最新正式 Release；
3. 全量静态/测试门；
4. v1.0.5 → v1.0.6 → v1.0.5 正式相邻升级/回滚；
5. updater helper 成功升级与失败自动回滚；
6. 固定 easychen/CookieCloud upstream 协议门；
7. 正式双架构 OCI index 构建及 AMD64、QEMU ARM64、原生 ARM64 对同一不可变 digest 的运行验证；
8. SBOM、release manifest、SHA256SUMS 的上传前校验与 GitHub Release 上传后重新下载回读；
9. 所有证据成功且再次确认当前最新正式 Release 后，才允许移动 stable / latest。

候选镜像不得作为正式生产部署身份，也不得替代正式 Release workflow 的重新验证。
