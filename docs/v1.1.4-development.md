## 1. 版本目标

### 1.1 目标一：一级菜单 + 二级菜单重构

v1.1.4 将当前扁平的一级导航改为四个一级业务域，并在需要的一级菜单下提供二级菜单：

| 一级菜单 | 二级菜单 |
| --- | --- |
| 总览 | 无 |
| 任务中心 | 数据拆包、数据去重 |
| 配置中心 | CookieCloud配置、站点配置、下载器配置 |
| 系统管理 | 通知配置、日志浏览、Agent配置、备份恢复 |

“关于”保留在页面右下角，不进入上述四个一级业务域。

### 1.2 目标二：站点配置页重构

站点配置页面采用已确认的方案 A：

- 缩小站点卡片，降低卡片高度和留白；
- 在相同屏幕宽度下提高单位面积的信息密度；
- 保持站点卡片清晰、易扫读；
- 卡片继续提供“查看详情 / 测试连接 / 编辑”等操作；
- 新增“查看详情”能力；
- 查看详情采用方案 D 的右侧详情抽屉；
- 详情抽屉中的个人信息、统计数据、连接状态全部只读；
- **详情抽屉不允许出现“编辑”按钮**；
- 修改站点配置仍通过卡片“编辑”进入原有配置弹窗。

当前实现存在以下与 v1.1.4 直接相关的结构：

6. 当前站点凭证已经通过 SecretStore 管理，详情接口不能因为新增详情能力而返回 Cookie、API Key、代理密码等敏感值。

# 4. 路由模型

## 4.1 不再使用“一级路由 + 页面内部 Tab”表达业务页面

当前的：

~~~text
任务中心
  └─ TaskCenterV2 内部 UNPACK / DEDUP

站点管理
  └─ 站点模式卡片
      ├─ 站点配置
      └─ CookieCloud 同步

系统设置
  └─ Tab
      ├─ 通知
      ├─ 下载器
      ├─ 日志
      ├─ AI 助手
      └─ 备份恢复
~~~

v1.1.4 改为真正的业务路由：

~~~text
任务中心 / 数据拆包
任务中心 / 数据去重

配置中心 / CookieCloud配置
配置中心 / 站点配置
配置中心 / 下载器配置

系统管理 / 通知配置
系统管理 / 日志浏览
系统管理 / Agent配置
系统管理 / 备份恢复
~~~

这样二级菜单本身就是功能入口，不再需要页面顶部额外的功能选择卡片或 Tab。

## 4.2 Hash 路由建议

继续使用现有 hash 路由机制，改为：

~~~text
#总览
#任务中心/数据拆包
#任务中心/数据去重
#配置中心/CookieCloud配置
#配置中心/站点配置
#配置中心/下载器配置
#系统管理/通知配置
#系统管理/日志浏览
#系统管理/Agent配置
#系统管理/备份恢复
#关于
~~~

要求：

- 路由解析集中在 frontend/src/navigation.ts；
- 一级、二级名称和路由不能散落在多个组件中；
- 提供统一的 route normalize / serialize；
- 非法路由自动回退到 #总览；
- 历史 URL 必须兼容迁移：
  - #站点管理 → #配置中心/站点配置
  - #系统设置 → #系统管理/通知配置
  - #下载器 → #配置中心/下载器配置
  - #日志 → #系统管理/日志浏览
  - #AI助手 / #AI 助手 → #系统管理/Agent配置
  - #关于继续有效。

# 9. 站点配置卡片方案 A

## 9.1 总体原则

当前站点卡片存在“内容不多但卡片很大”的问题。

v1.1.4 不通过继续增加无意义信息填充卡片，而是：

> **缩小卡片 + 提高信息密度 + 将扩展信息移入详情抽屉。**

## 9.2 卡片布局

桌面端建议：

~~~css
grid-template-columns: repeat(auto-fill, minmax(220px, 1fr));
gap: 12px ~ 14px;
~~~

具体列数根据可用内容区自动适配。

要求：

- 1440px / 2K 桌面宽度下优先保持 4 列；
- 打开右侧详情抽屉后，剩余内容区域重新自适应；
- 不允许因为抽屉打开导致横向滚动；
- 1280px 以下自动降低列数；
- 移动端自动单列。

## 9.3 卡片高度

建议：

- 卡片整体高度控制在约 300px 以内；
- 减少上下 padding；
- 信息行高度控制在 28～32px；
- 不展示只有为了“撑高卡片”而增加的字段；
- 站点 URL 不在卡片中展示完整长 URL；
- 长文本统一 ellipsis + Tooltip。

## 9.4 卡片信息层级

### 第一层：站点识别

~~~text
[站点 Logo]  M-Team
             综合类
                         ● 在线
~~~

### 第二层：核心用户信息

~~~text

用户等级      Power User
~~~

### 第三层：核心统计

~~~text
上传量        12.34 TB
下载量        1.23 TB
分享率        10.02
做种数        256
~~~

### 第四层：最后同步

~~~text

~~~

### 第五层：操作


“查看详情”为主操作。

# 14. “历史同步”Tab

## 14.1 目的

用于查看站点用户信息同步历史，而不是站点业务历史。

每次同步记录：

~~~text
同步时间
状态
耗时
获取字段数量
失败原因
~~~

示例：

~~~text
2026-10-16 10:30:22    成功    128 ms
2026-10-16 04:30:16    成功    143 ms
2026-10-15 22:30:08    失败    Cookie 无效
~~~

## 14.2 保存策略

建议新增轻量级站点用户同步记录。

原则：

- 最新成功数据单独保存；
- 同步历史保留有限条数；
- 默认每站保留最近 30 条；
- 超出后删除最旧记录；
- 不保存 Cookie/API Key 等敏感信息；
- 失败记录也保存，但只保存错误码、摘要，不保存完整响应正文。

# 15. 站点详情后端设计

## 15.1 复用现有领域能力

当前已经存在：

~~~python
class SiteAdapter(Protocol):
    async def capabilities(...)
    async def test_connection(...)
    async def fetch_user_profile(...)
    async def search(...)
    async def fetch_details(...)
    async def fetch_torrent(...)
~~~

因此 v1.1.4 不重新建立一套站点抓取框架。

详情服务应：

~~~text
SiteService
   ↓
Enabled / configured site snapshot
   ↓
SiteAdapterFactory
   ↓
具体 SiteAdapter
   ↓
fetch_user_profile()
   ↓
统一 SiteUserProfile
~~~

站点差异继续封装在 Adapter 中。

### Rousi Pro HTTP/2 兼容要求

Rousi Pro 的用户资料只读接口在当前真实环境中需要通过 HTTP/2 建立稳定连接，因此 Rousi Pro Adapter 的真实网络客户端必须：

- 使用 httpx2.AsyncClient(http2=True)；
- 项目依赖必须启用 httpx2[http2]；
- 锁文件必须包含 h2 及其依赖；
- 不允许通过关闭 HTTP/2 回退到不稳定的 HTTP/1.1 作为生产方案；
- 仍保持 API Key 只用于已审查的只读接口，不得扩展到公开搜索或未经验收的接口。



同一站点同时只能存在一个用户信息同步任务，避免重复点击产生并发请求。
