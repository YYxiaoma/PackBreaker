# PackBreaker v1.0.15 研发说明

## 1. 版本目标

v1.0.15 对“拆包”能力做一次面向最终产品形态的重构，不继续在现有手动拆包 / 监控拆包旧模型上增量叠加。

本版本以 [`docs/prototypes/unpack-flow-v2.html`](./prototypes/unpack-flow-v2.html) 为已确认 UI / 交互基线，目标是把前端原型收敛为一套统一、可分页、可恢复、可人工审核的数据拆包执行链。

同时修复 v1.0.13 现场日志暴露的在线升级错误诊断问题：后端已经明确返回结构化 5xx 时，前端不得继续误报为“升级请求结果暂时未知”。

## 2. 开发阶段与兼容性决策

当前项目仍处于测试阶段，没有真实用户和需要保留的历史任务数据。

因此 v1.0.15 明确采用以下策略：

1. 不为旧手动拆包 / 监控拆包任务定义做数据兼容。
2. 不为旧执行记录、旧候选审核状态做数据迁移保真。
3. 允许删除旧表、旧字段、旧状态和旧 API 后重新建立新的统一模型。
4. Alembic 仍需有明确 migration，使 fresh DB 和研发环境能够稳定进入新 head；migration 可以采用“删除旧任务数据后重建新模型”的破坏性方案。
5. 不再保留仅为历史版本兼容存在的前端判断和后端分支。
6. 源媒体安全、路径授权、operation journal、下载器安全写入、凭证保护等安全不变量不能因为放弃旧数据兼容而降低。

## 3. 任务中心产品结构

任务中心顶部由原来的三张卡片：

- 手动拆包；
- 监控拆包；
- 影片去重；

调整为两张一级卡片：

- **数据拆包**
- **数据去重**

“数据拆包”内部仍保留任务触发方式：

- 手动拆包；
- 监控拆包。

两种任务只负责“如何产生一次执行”，进入执行后使用完全相同的数据发现、影片匹配、人工审核和拆包执行链。

“数据去重”本版本只调整一级入口命名与任务中心聚合方式，不重构既有去重执行逻辑。

## 4. 新增数据拆包任务

新增任务表单固定为五个区块。

### 4.1 基本信息

字段：

- 任务名称；
- 任务类型：手动拆包 / 监控拆包；
- 扫描站点，多选；
- 执行时间，仅监控拆包显示。

监控任务的 Cron / 调度能力仍存在，但调度只负责创建新的执行实例，不再拥有单独的媒体匹配实现。

监控任务的“执行时间”增加 Cron 辅助组件：

- 保留 Cron 表达式输入框；
- 提供“每 5 分钟 / 每 10 分钟 / 每小时 / 每天 03:00 / 每周一 03:00”等常用预设；
- 提供“分钟 / 小时 / 日期 / 月份 / 星期”五段可点击选择器；
- 点击预设或任意分段后立即回填 Cron 表达式；
- 用户仍可直接编辑表达式；
- 本版本只支持标准 5 段 Cron，不引入秒字段；
- 前端显示最近一次解析结果或中文执行说明，服务端仍负责最终 Cron 合法性校验。

### 4.2 来源

来源支持：

- 目录；
- 下载器。

目录选择按钮统一改成“文件 / 目录树”弹窗。

目录树要求：

- 从管理员已经显式挂载并授权的根目录开始；
- 目录节点按需展开，不一次递归扫描全盘；
- 能显示文件与目录；
- 手动任务允许展开到文件级查看；
- 监控任务以选中的目录节点作为监控根；
- 支持目录搜索；
- 右侧展示当前选择路径、类型、子对象数量和估算大小；
- 选择结果必须经过服务端路径授权重新验证，不能只信任前端节点。

### 4.3 文件过滤

保留：

- 文件类型；
- 最小大小；
- 最大大小；
- 包含名称；
- 排除名称；
- 忽略临时文件；
- 包含子目录。

新增：

- **后缀名过滤**

后缀名过滤采用白名单语义，例如：

```text
.mkv, .mp4, .ts
```

规范化要求：

- 自动 trim；
- 自动转小写；
- 缺少前导 `.` 时可规范化为带 `.`；
- 去重；
- 拒绝空值、路径分隔符、NUL 和超长值；
- 不根据 MIME 猜测后缀。

### 4.4 输出与文件冲突

本轮产品交互保持现有概念：

- 输出目录；
- 存放方式；
- 文件冲突策略。

执行层仍必须遵守现有源数据只读、目标 ownership、inode、跨设备 hardlink 和 operation journal 安全约束。

### 4.5 高级执行规则

保留并新增：

- 自动重试开关；
- 自动重试次数；
- 自动匹配阈值（0.0%～100.0%，默认 100.0%）。

“自动匹配阈值”只决定候选是否可以跳过人工选择。例如阈值为 95.0%，最佳候选评分达到 95.0% 且不存在 hard conflict 时，可自动选中该候选并进入种子内容校验。

自动匹配阈值不是辅种安全阈值。即使候选达到 100%，在真正执行辅种前仍必须下载候选 `.torrent`，按 torrent piece / Merkle 元数据对本地文件做只读内容验证；内容验证不通过时禁止进入辅种执行。

以下旧高级选项从新增任务表单删除，不再作为用户可配置任务定义：

- 稳定检测；
- 稳定等待；
- 仅处理下载完成；
- 首次扫描范围；
- 修改静默窗口；
- Cron 重叠策略；
- 高风险预授权；
- 预授权 Action。

若其中仍有必要的底层安全行为，应转化为服务端固定策略，而不是继续暴露为任务级可配置项。

### 4.6 保存与执行分离

新增数据拆包任务底部按钮由“保存并执行”调整为“保存”。

保存操作只创建任务定义，不创建 execution。所有新建任务保存成功后的前端状态统一显示为“待执行”，任务列表操作列提供独立“执行”按钮。

执行规则：

- 手动拆包：点击“执行”后才创建一次新的 execution；
- 监控拆包：保存后同样为“待执行”，点击“执行”后启用该监控任务，之后按 Cron / 来源规则产生 execution；
- 保存动作本身不得调用站点搜索、下载 torrent、修改文件系统或写下载器。

#### 4.6.1 手动拆包 + 目录来源的执行范围确认

当任务类型为“手动拆包”且来源为“目录”时，点击“保存”后先弹出确认框：

> 是否将该目录下所有影视文件进行拆包？

选择“是”：

- 直接完成任务创建；
- 执行范围保存为 `ALL_MATCHING_MEDIA`；
- 状态为“待执行”；
- 后续点击“执行”时，才按任务文件过滤规则重新扫描目录中的全部影视文件。

选择“否”：

- 暂不完成任务创建；
- 服务端扫描该目录下符合基础媒体识别规则的影视文件；
- 打开“选择需要拆包的影视文件”弹窗；
- 只有用户最终勾选的影视文件进入任务执行范围；
- 用户点击“保存任务”后才正式创建任务，并进入“待执行”。

影视文件选择弹窗顶部必须提供过滤组件，至少包括：

- 影片名称 / 路径关键字；
- 后缀；
- 分辨率；
- 已勾选 / 未勾选状态。

同时提供“勾选当前结果 / 取消当前结果”。顶部过滤只影响当前列表展示，不得因为过滤条件变化自动取消已经勾选的其他影片。

选定影视文件模式保存为 `SELECTED_MEDIA`，持久化稳定 source object identity。真正点击“执行”时只发现这些选定对象，并重新校验路径授权、文件是否仍存在和 source snapshot；不能因为目录中新加入了影片而扩大本次任务范围。

## 5. 统一数据拆包执行链

手动任务和监控任务共用以下六阶段：

1. 分页获取影片；
2. 分批影片匹配；
3. 自动匹配 / 人工审核；
4. 种子内容校验；
5. 辅种执行；
6. 客户端校验 / 完成。

### 5.1 分页获取影片

执行开始后，不一次把全部媒体对象加载到内存。

要求：

- 服务端按稳定排序分页发现符合来源与文件过滤条件的媒体；
- 每页生成持久化 execution item；
- 使用 cursor / continuation token，而不是依赖大 offset 做全目录翻页；
- 默认后台发现页大小建议 100，UI 查询页大小默认 20；
- UI 展示页大小不影响后台执行批次。

每个 execution item 至少记录：

- 源对象唯一键；
- 源路径快照；
- 文件大小；
- 修改时间 / inode 等安全快照；
- 解析后的影片标题；
- 年份；
- IMDb ID；
- 豆瓣 ID；
- 分辨率；
- 来源介质；
- 制作组；
- 当前匹配状态。

### 5.2 分批影片匹配

分页发现与匹配解耦。

匹配 worker 按固定小批次领取待匹配 item，默认建议 20 个。

单个影片搜索优先级：

1. IMDb ID；
2. 豆瓣 ID；
3. 规范化影片名 + 年份；
4. 必要时退化到规范化影片名。

若同时存在多个稳定外部 ID，允许并行或顺序查询，但必须对同一站点结果去重。

站点返回结果必须先经过相关性门，再进入评分。

### 5.3 候选评分

匹配度是“候选排序与自动确认决策”，不是文件内容安全证明。

评分证据可包含：

- IMDb ID 一致；
- 豆瓣 ID 一致；
- 标题 / 别名一致；
- 年份一致；
- 分辨率一致；
- 来源类型一致；
- 制作组一致；
- 文件大小 / 总大小接近；
- 其他当前领域层已经验证为可靠的媒体元数据。

评分结果保存为结构化 evidence，前端人工审核必须能解释“为什么是 96.8%”，不能只展示裸分数。

### 5.4 自动匹配阈值

任务定义保存用户配置的自动匹配阈值，默认 100.0%。

候选满足以下条件时可自动选中：

- 匹配度 `>= 自动匹配阈值`；
- 不存在 hard conflict；
- 候选仍属于当前 candidate generation。

自动选中后：

- item 状态进入 `MATCHED_AUTO`；
- 保存选中候选；
- 保存完整评分证据；
- 继续进入种子内容校验。

自动匹配只表示“无需人工选择候选”，不表示该 torrent 已证明可以辅种。

### 5.5 低于阈值候选进入人工审核

最佳候选低于任务配置的自动匹配阈值，或者存在需要人工判断的元数据冲突时，不自动批准。

要求：

- 保存当前搜索得到的完整候选列表；
- 按匹配度降序排列；
- item 状态进入 `REVIEW_REQUIRED`；
- execution 聚合状态显示“待人工审核”；
- 前端打开审核弹窗时默认选中最高匹配度候选；
- 默认选中只是一种 UI 初始值，不等于服务端审批；
- 必须由用户点击“确认所选候选并继续”后才持久化 `MATCHED_MANUAL`。

用户还可以：

- 选择其他候选；
- 标记无匹配；
- 稍后处理。

### 5.6 自动匹配结果也允许人工审核

执行详情中，状态为“自动匹配成功”的影片在操作列显示“审核”按钮。

点击后进入与待人工审核相同的候选列表：

- 默认仍选中当前自动匹配候选；
- 可以改选其他候选；
- 可以标记无匹配；
- 若 item 尚未进入外部副作用阶段，提交新的审核结果会废弃原自动选择及其未执行计划；
- 若已经进入辅种外部副作用阶段，则审核弹窗只允许查看，必须先取消并完成安全回滚后才能修改候选。

### 5.7 种子内容校验

候选被自动匹配或人工确认后，必须先获取候选 `.torrent` 并进行内容级验证。

注意：BitTorrent info hash 是对 torrent `info` 元数据的摘要，不是影片文件整体 hash，不能拿 info hash 与本地影片 SHA-1 / SHA-256 直接比较。

内容验证按 torrent 类型执行：

- v1：按照 torrent 文件顺序和 piece 边界读取本地逻辑字节流，逐 piece 计算 SHA-1，与 `pieces` 中的 piece hash 比较；
- v2：按 BEP 52 使用 SHA-256 Merkle `pieces root` / piece layers 验证每个文件；
- hybrid：v1 与 v2 两套证据都必须通过。

只有内容级验证得到 `FULL_VERIFIED`，才允许进入自动辅种执行。

如果候选元数据评分很高但内容 hash 不一致：

- 当前候选标记为“内容不一致”；
- 不创建辅种副作用；
- 若站点能力和候选验证预算允许，可继续验证下一条候选；
- 否则回到“待人工审核”，展示“元数据匹配但内容校验失败”的证据。

人工审核选择的非 100% 候选也走完全相同的内容验证；只要内容 `FULL_VERIFIED`，就可以正常辅种。反之，即使用户手动选中，也不能把内容不一致的文件当作辅种成功。

#### 5.7.1 Torrent 包含 `.nfo`、海报等辅助文件

PT torrent 经常包含主影片之外的 `.nfo`、`.jpg`、`.jpeg`、`.png`、`.webp`、字幕或其他小型 sidecar 文件。本地只有主影片时，不应因为这些辅助文件缺失就直接判定“影片不匹配”。

本版本把 torrent 文件分成：

- 主媒体文件：必须与本地影片建立可信映射；
- 可补齐辅助文件：允许本地缺失，由下载器在隔离 staging 中补齐；
- 协议 padding / zero-length：按协议规则处理；
- 其他媒体文件：默认仍视为必需内容，不因为扩展名相似而自动忽略。

辅助文件缺失时执行：

1. 主影片先完成文件名 / 大小 /媒体身份映射；
2. 候选进入“辅助文件待补齐”，不能直接创建源影片硬链接；
3. 在 PackBreaker 管理的隔离 staging 目录中，以暂停状态加入候选 torrent；
4. 通过下载器的按文件选择能力，仅请求缺失辅助文件；
5. v1 torrent 即使 piece 跨越主影片与辅助文件边界，下载器也只会在 staging 中写入边界 piece，不接触源影片；
6. 辅助文件就绪后，使用“本地主影片 + staging 辅助文件”重新执行完整 v1 / v2 / hybrid 内容验证；
7. 只有整包达到 `FULL_VERIFIED`，才创建最终目录中的主影片 hardlink / symlink / copy；
8. 已下载的 `.nfo` / 海报等辅助文件由 PackBreaker 移入最终目标目录；
9. 最后让下载器对最终目录执行客户端校验，确认 100% 后进入做种。

因此：如果 torrent 中主影片与本地影片完全一致，只是本地缺少 `.nfo` / 海报，**应当能够匹配并最终辅种成功**；差异只体现在中间多一个“补齐辅助文件”阶段。

自动补齐只适用于明确白名单中的小型辅助文件。若 torrent 还包含另一个正片、额外集数、花絮视频或其他大媒体文件，本版本默认不能把它当作可忽略 sidecar，必须按必需内容处理。

### 5.8 辅种执行

内容验证通过后，执行顺序为：

1. 再次核对 source snapshot，确认本地影片在 hash 验证后没有变化；
2. 根据输出策略生成 Execution Plan；
3. 执行路径、inode、跨设备 hardlink、ownership 等安全检查；
4. 先写 operation journal intent；
5. 创建 hardlink / symlink / copy 等目标文件；
6. 将已安全补齐的辅助文件布置到最终目标目录；
7. 将候选 torrent 添加 / 迁移到目标下载器最终目录，初始保持安全状态；
8. qBittorrent 只有在领域验证与客户端 capability 同时允许时才可以跳过重复校验；
9. Transmission 始终执行客户端 verify；
10. 确认下载器识别为 100% 完成并进入做种状态；
11. 写入 operation journal result 并完成 item。

如果下载器最终校验不是 100%，不能把任务标记为辅种成功；按既有安全策略进入阻断、对账或安全修复链，且不得修改源影片。

### 5.9 匹配超时与匹配错误

单个 item 可以进入：

- `MATCH_TIMEOUT`
- `MATCH_ERROR`

列表和执行详情在异常状态右侧直接展示“重试”。

重试要求：

- 只重试指定失败 item，不重复扫描整个来源；
- 使用持久化 retry count；
- 自动重试和手动重试必须进入同一状态机；
- 自动重试次数达到上限后保持异常状态等待人工操作；
- 搜索类 GET / 只读请求可以按明确的幂等策略重试；
- torrent 下载 token 等不可安全重试请求继续遵守站点适配器既有规则。

## 6. 手动拆包任务

保存后任务先进入“待执行”，不自动创建 execution。用户从任务列表点击“执行”后：

1. 冻结任务配置快照；
2. 创建 execution；
3. 根据执行范围处理来源：`ALL_MATCHING_MEDIA` 重新分页扫描目录；`SELECTED_MEDIA` 只解析保存时选定的 source object identity；
4. 分批执行影片匹配；
5. 达到自动匹配阈值的候选自动选中；
6. 低于阈值候选进入人工审核；
7. 已选候选下载 `.torrent` 并做 v1 / v2 / hybrid 内容验证；
8. 只有 `FULL_VERIFIED` item 进入辅种执行；
9. 完成下载器 / 文件系统校验；
10. 收敛 execution。

手动任务允许用户在执行过程中暂停 / 恢复，但不得通过重新点击“执行”创建与同一 execution 重叠的重复副作用。

任务处于“待执行”时允许修改定义；一旦创建 execution，该 execution 使用冻结配置和执行范围快照，后续编辑任务定义不能改变已经开始的 execution。

## 7. 监控拆包任务

监控任务只与手动任务在“触发”上不同。

每次调度触发：

1. 根据目录或下载器来源读取新增 / 待处理对象；
2. 生成新的 execution；
3. 后续完全复用手动任务执行链。

监控任务不再维护第二套候选评分、人工审核或拆包状态机。

当监控任务来源选择“下载器”时，新增任务表单必须显示：

- 下载器实例；
- 任务名称包含；
- 分类；
- 标签；
- 输出目录。

服务端固定只把已经下载完成、文件状态稳定的下载器任务送入媒体发现链，不再把“仅处理下载完成”暴露为可关闭的高级选项。

相同源对象必须使用稳定 source identity + task definition 去重，避免每次 Cron 重复创建执行项。

## 9. 人工审核

人工审核视图必须显示源影片的关键字段：

- 原文件 / 目录名；
- IMDb；
- 豆瓣 ID；
- 年份；
- 分辨率；
- 来源；
- 大小；
- 制作组。

每条候选至少显示：

- 站点；
- torrent / 候选 ID；
- 标题；
- 大小；
- IMDb / 豆瓣 ID；
- 做种数等站点允许公开的只读信息；
- 匹配度；
- 匹配证据。

## 10. 数据库重构

由于不保留旧任务数据，本版本可以直接废弃旧拆包相关表模型，建立新的核心表：

- `unpack_definition`
- `unpack_execution`
- `unpack_execution_item`
- `unpack_match_candidate`
- `unpack_review_decision`
- `unpack_definition_selected_source`

以上六张为核心拆包业务表。保存前“选择影片”另使用两张临时辅助表：

- `unpack_source_scan`
- `unpack_source_scan_item`

临时 scan 默认 30 分钟过期；任务创建时将最终勾选项物化到核心执行范围表后删除临时 scan。selection token 不授予权限，所有目录访问都必须重新经过 `AuthorizedPathScope` 校验。

文件系统副作用和下载器副作用继续复用 operation journal，不重复建立新的低安全等级日志表。

具体字段、索引和关系见 API / 数据模型设计文档。

- definition_id；
- execution_id；
- item_id；
- site_id；
- trace_id。

重点事件：

- 分页发现开始 / 完成；
- 批次匹配开始 / 完成；
- 搜索依据选择；
- 候选数量；
- 达到阈值自动匹配；
- 自动匹配人工复核；
- torrent 获取与内容校验；

## 13. 在线升级 503 诊断修复

v1.0.13 现场日志显示 `/api/v1/system/upgrade/actions` 会明确返回 HTTP 503，但前端把所有 5xx 都提示成：

```text
升级请求结果暂时未知；请用同一按钮重试确认，不要重复发起新升级。
```

这会掩盖服务端已经明确给出的失败原因。

v1.0.15 修复规则：

1. `API_UNAVAILABLE`、真正没有结构化响应的泛化 5xx、408 / 504 才视为“结果可能未知”。
2. 后端已经返回稳定业务 `code` 的 5xx 必须视为确定失败，并直接展示脱敏错误信息。
3. transient updater 在 `build_replacement_plan()` 阶段遇到安全的 `DockerUpdaterError` 时，保留原始稳定错误码，例如：
   - `UPGRADE_MULTI_NETWORK_UNSUPPORTED`
   - `UPGRADE_STATIC_NETWORK_ADDRESS_UNSUPPORTED`
   - `UPGRADE_CONFIG_MOUNT_INVALID`
   - `UPGRADE_MOUNT_UNSUPPORTED`
4. 只有无法区分的 helper bootstrap I/O / Docker 通信异常才使用 `UPDATER_BOOTSTRAP_FAILED`。
5. 明确失败后清理前端 pending upgrade 状态；真正结果未知时保留原 Idempotency-Key 用于重试确认。

## 14. 非目标

本版本不做：

- 数据去重执行引擎重构；
- 新站点接入；
- 新下载器类型；
- AI 自动替用户做候选审核；
- 仅凭匹配分数绕过 torrent / 文件系统安全验证；
- 旧任务定义数据保留；
- 旧执行历史迁移。

## 15. 实施顺序

建议按以下顺序开发：

1. 删除旧拆包领域模型中的兼容包袱并落新 schema。

6. 完成人工审核 API。

9. 完成目录树 API 与新任务表单。

11. 接执行详情与审核弹窗。
12. 删除旧 API / 旧组件 / 旧状态。
13. 完成在线升级 503 诊断修复。
14. 全量自动化与候选镜像验收。

## 16. 完成标准

v1.0.15 只有同时满足以下条件才视为完成：

- UI 与已确认静态原型一致；
- fresh DB 可直接进入新 schema head；
- 旧拆包任务表可以被破坏性清理，不残留双模型；
- 手动 / 监控任务真实共用同一 execution pipeline；
- 保存任务不会创建 execution，新建任务统一显示“待执行”；
- 任务列表提供独立“执行”按钮；
- 手动 + 目录任务保存时必须完成“全部影视文件 / 选择影片”范围确认；
- 选择影片模式支持顶部过滤，且只有最终勾选项会进入执行范围；
- ALL_MATCHING_MEDIA 在点击执行时重新扫描目录，SELECTED_MEDIA 不会因目录新增文件而扩大范围；
- 大目录能够分页发现，不一次加载全部媒体；
- 匹配能够按批次恢复；
- 自动匹配阈值可配置且默认 100.0%；
- 达到阈值的候选可自动选中，低于阈值进入人工审核；
- 自动匹配成功项提供“审核”入口；
- 人工审核默认选择最高候选但不会自动提交；
- 自动或人工选择的候选都必须通过 torrent 内容级 `FULL_VERIFIED` 才能进入自动辅种；
- v1 / v2 / hybrid 内容校验都有自动化覆盖；
- 内容不一致时不会创建辅种副作用；
- 匹配超时 / 错误支持 item 级重试；
- 监控拆包可选择下载器来源并支持名称 / 分类 / 标签过滤；
- 目录树选择服务端继续失败关闭；
- 文件后缀过滤有单元 / API / E2E 覆盖；
- operation journal、源数据只读和下载器安全门继续成立；
- 所有前端状态、阶段和错误字段均中文展示；
- 在线升级明确 503 能显示具体错误，而不是错误提示“结果未知”；
- Ruff、mypy、pytest、Vitest、Vue TypeScript、Vite build、Playwright、Docker candidate E2E 全部通过。
