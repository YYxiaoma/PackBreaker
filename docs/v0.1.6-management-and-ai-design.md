# PackBreaker v0.1.6 管理体验与智能助手开发文档

> 状态：已确认研发基线  
> 版本目标：v0.1.6  
> 说明：本文件已经完成需求确认，作为 v0.1.6 后续研发、测试和验收的产品基线。此前讨论中的设计建议均已采纳；文中“建议”主要表示推荐实现方式，不再代表待用户确认的产品决策。后续如需改变本文件已冻结的产品口径，应先更新文档再进入实现。

## 1. 版本目标

v0.1.6 不改变 v0.1.5 已完成的任务中心、安全执行链、operation journal、源文件保护和人工确认原则，重点改善系统配置与日常管理体验，并扩展站点覆盖范围、下载器运行信息、通知中心和登录账户体验，同时加入 AI 助手的第一版产品骨架。

本版本包含六个主要工作域：

1. 下载器页面逻辑与运行指标重构。
2. 站点管理页面、站点类型、连接参数与用户详情重构。
3. 通知渠道配置与事件订阅重构。
4. 登录、用户头像、通知中心与修改密码体验重构。
5. 系统设置新增 AI 助手配置、只读智能诊断与 Telegram AI 对话。
6. 新增“关于”页面。

### 1.1 不变的安全边界

- 站点 Cookie、API Key、代理密码、下载器密码、通知渠道凭证和 AI Provider API Key 必须进入 `SecretStore`，任何 GET API 不返回明文。
- 新增的测试连接、站点用户信息获取、下载器指标获取均为只读能力，不得借此绕过任务中心的预演、确认和执行安全门。
- 现有拆包、hardlink、下载器添加/校验/启动/移除、repair、rollback、retention 等副作用链保持现有 journal、幂等和当前性检查。
- UI 中的状态、统计数据和 AI 结论只作为信息展示，真正的写操作权限继续由后端领域服务判断。

## 2. 下载器页面逻辑调整

### 2.1 需求基线

1. “新增下载器”弹窗和下载器卡片/列表中删除“监控分类标签”。
2. “添加下载器”页面增加“测试连接”按钮。
3. 删除下载器页面左上角“下载器实例”文本标题/说明字段，减少无价值页面占位。
4. 下载器卡片新增运行数据：
   - 当前上传速度；
   - 当前下载速度；
   - 当前文件总大小；
   - 剩余磁盘空间；
   - 后续可根据下载器能力扩展活动任务数、暂停任务数等数据。

### 2.2 建议的数据定义

为避免 qBittorrent 与 Transmission 两种客户端显示口径不一致，建议统一为 `DownloaderRuntimeMetrics`：

| 字段 | 含义 | 展示建议 |
| --- | --- | --- |
| `upload_speed_bytes_per_second` | 下载器当前全局上传速度 | KiB/s、MiB/s 自动换算 |
| `download_speed_bytes_per_second` | 下载器当前全局下载速度 | KiB/s、MiB/s 自动换算 |
| `total_content_size_bytes` | 当前下载器任务集合的总内容大小 | GiB/TiB |
| `free_space_bytes` | 当前主下载目录可用空间 | GiB/TiB |
| `active_torrent_count` | 当前活动任务数 | 可选 |
| `total_torrent_count` | 当前任务总数 | 可选 |
| `sampled_at` | 指标采样时间 | 用于判断数据是否陈旧 |

“当前文件总大小”建议正式定义为**当前下载器全部任务的内容总大小**，避免与单个正在下载文件或 PackBreaker 自身 `/data` 大小混淆。如果实际期望是“活动任务总大小”，研发前再调整字段名称和口径。

### 2.3 API 与刷新建议

- 新增只读 `GET /downloaders/{id}/metrics`，由后端适配器统一 qB/TR 的统计字段。
- 下载器列表建议由页面级定时器统一刷新，默认 10～15 秒一次，避免每张卡片独立轮询形成请求风暴。
- 下载器离线时卡片保留配置本身，但运行指标显示 `--` 或“不可用”，同时显示最后一次成功采样时间，不使用旧数据伪装成实时数据。
- 剩余磁盘空间优先使用下载器自身对下载目录的统计；客户端不提供时才考虑由已经验证过的路径映射安全回退到服务端文件系统统计，并明确标记数据来源。

### 2.4 “新增时测试连接”的实现建议

当前保存后测试与“新增表单尚未保存”是两个不同场景。建议增加**临时探测接口**，例如：

`POST /downloaders/probe`

请求可以携带尚未保存的类型、地址和凭证，只进行一次只读连接测试，不创建数据库记录、不保存 Secret、不回显密码。测试成功后用户再点击保存。

现有 `POST /downloaders/{id}/test` 继续用于已保存实例。

### 2.5 关于 `monitor_rules` 的建议

当前数据库与 API 仍存在 `monitor_rules`，前端“监控分类”只是其中一个使用方式。建议 v0.1.6 分两步处理：

- 产品层立即删除该配置项和卡片展示；
- 后端先停止新写入 `monitor_rules.category`，但不要在同一版本直接做破坏性删列迁移；确认没有其他运行时依赖后，再在后续兼容迁移中移除旧字段。

这样可以避免 UI 删除一个字段时同时引入不必要的数据库升级风险。

### 2.6 验收口径

- 新增/编辑下载器不再出现监控分类。
- 未保存下载器可以执行测试连接，测试不会新增数据库记录。
- qBittorrent 与 Transmission 卡片都使用统一指标结构；不支持的字段明确显示不可用。
- 页面切换、关闭或组件卸载后停止指标轮询。
- 下载器不可达不会影响其他卡片刷新。

## 3. 站点管理页面逻辑调整

### 3.1 站点类型范围

v0.1.6 计划支持以下站点类型：

- M-TEAM
- HHClub
- KeepFrds
- HDHome
- Ubits
- HDTime
- HDFans
- BTSCHOOL
- PTTime
- Rousi Pro

当前已有真实适配基础的 M-TEAM、HHClub、HDTime 继续沿用；其余站点需要在用户后续提供合法的 Cookie 或 API Key 后完成适配、共享契约测试和真实只读验收。

### 3.2 固定站点 Profile Registry

用户不再手工输入站点地址。建议后端建立固定的 `SiteProfileRegistry`，每种站点类型维护：

- `kind`
- 展示名称
- 固定官方 `base_url`
- 凭证类型：`API_KEY` / `COOKIE`
- 默认超时时间
- 默认搜索间隔
- 是否支持 User-Agent
- 是否支持浏览器请求头仿真
- 是否支持代理
- 适配器类型与能力集

站点 URL 必须由后端 Profile 决定，前端只展示只读地址或直接不展示。新增新站点时应修改代码中的受审查 Registry，而不是让数据库中的任意 URL 决定 Cookie/API Key 的发送目标。

这项调整同时增强凭证安全：可以避免用户误填第三方地址后把站点 Cookie/API Key 发给非目标域名。

### 3.3 添加站点页面

需求字段整理如下：

| 配置 | 展示条件 | 建议 |
| --- | --- | --- |
| 站点名称 | 全部 | 保留，可默认使用站点类型名称，允许用户区分多个账号 |
| 站点类型 | 全部 | 必填，下拉选择 Registry 中类型 |
| 站点地址 | 删除 | 地址由站点类型固定绑定 |
| 凭证 | 全部 | API Key 或 Cookie，只写不回显 |
| 测试连接 | 全部 | 支持尚未保存的临时探测 |
| 启用状态 | 全部 | Radio / Switch；实际启用仍建议要求最近一次测试成功 |
| 超时时间 | 全部 | 秒；建议默认 15 秒，限定合理上下界 |
| 搜索间隔 | 全部 | 秒；供任务分析调用站点搜索时执行最小间隔控制 |
| User-Agent | Cookie 站点 | 文本框；提供安全默认 UA，可自定义 |
| 浏览器仿真 | Cookie 站点 | Radio / Switch |
| 使用代理服务器 | 建议全部站点可用 | Radio / Switch |
| 代理地址 | 启用代理 | 主机/IP，不包含协议凭证 |
| 代理端口 | 启用代理 | 1～65535 |
| 代理账号 | 启用代理且需要认证 | 可选 |
| 代理密码 | 启用代理且需要认证 | SecretStore，只写 |

### 3.4 浏览器仿真的边界建议

“浏览器仿真”首版建议定义为**受控 HTTP 请求 Profile**，例如 User-Agent、Accept、Accept-Language、Referer/Origin 等站点适配器明确需要的普通请求头，而不是在 v0.1.6 直接引入完整 Headless Browser。

如果目标站点出现 JavaScript Challenge、验证码或其他交互挑战，适配器应明确返回不支持/需要人工更新凭证，而不是自动尝试绕过站点安全机制。这样可显著降低实现复杂度和账号风险。

### 3.5 临时测试连接

建议新增：

`POST /sites/probe`

它与下载器临时探测相同：使用表单中的未保存凭证执行只读测试，完成后立即丢弃明文，不创建 Site 或 Secret 记录。

如果新增表单选择“启用”，建议流程为：

1. 保存站点配置；
2. 执行真实只读连接测试；
3. 仅测试成功后才将实际 `enabled=true`；
4. 失败时保留配置但实际保持禁用，并展示错误原因。

不建议让“Radio 选中启用”绕过当前已有的连接证据安全门。

### 3.6 站点管理主页面

需求调整：

- 删除页面左上角“站点配置”文本标题/说明。
- 删除独立“站点健康与可靠性”列表。
- 将日常需要的状态浓缩进站点卡片。
- 站点名称旁显示连接状态点。
- 卡片增加“详情”按钮。

建议状态点采用统一四态，而不仅仅绿色/红色：

| 状态 | 颜色 | 含义 |
| --- | --- | --- |
| `OK` | 绿色 | 最近一次连接/鉴权正常 |
| `DEGRADED` | 黄色/橙色 | 限流、临时故障、熔断 HALF_OPEN 等可恢复状态 |
| `FAILED` | 红色 | 鉴权失败、持续连接失败或熔断 OPEN |
| `UNTESTED` / `DISABLED` | 灰色 | 尚未测试或站点已停用 |

“已启用/已停用”与“连接正常/失败”是两个维度，建议不要用同一个状态点同时表达两者。启用状态继续使用独立开关或 Tag。

### 3.7 站点详情

点击“详情”建议打开抽屉或大尺寸 Dialog，而不是跳转新页面。详情数据定义为统一的 `SiteUserProfile`，允许不同站点缺少部分字段：

- UID
- 用户名
- 用户等级
- 真实上传量
- 真实下载量
- 上传量
- 下载量
- 分享率
- 发种数
- 做种数
- 做种量
- 魔力值
- 做种积分
- 每小时魔力值
- 数据更新时间 `fetched_at`

所有数值字段都应允许 `null`，由前端显示 `--`。不能因为某个站点没有“每小时魔力值”就伪造 `0`。

建议新增：

`GET /sites/{site_id}/profile`

该接口只在用户打开详情或点击刷新时访问远端，并允许短 TTL 缓存。**不要在站点列表每次刷新时同时拉取所有用户详情**，否则十个站点很容易造成不必要的请求和封禁风险。

### 3.8 站点适配建议

站点类型增加不等于适配器已经可用。每个站点进入“正式支持”前至少需要通过：

1. 登录/鉴权探测；
2. 用户信息读取；
3. 搜索；
4. 详情；
5. `.torrent` 获取；
6. 最小请求间隔；
7. 错误分类；
8. Cookie/API Key 不泄露测试；
9. 真实只读验收；
10. 至少一条与现有任务 Analyze 链的受控集成测试。

建议为新站点显示支持状态，例如“可配置 / 已完成适配 / 待真实验收”，避免 UI 出现站点类型后让用户误以为所有搜索能力均已完成。

## 4. 通知渠道设置重构

### 4.1 需求基线

- “添加渠道”按钮移动到页面最右侧。
- 添加/编辑渠道弹窗删除：
  - 任务基础链接地址；
  - 重复事件聚合窗口组件。
- 新增：
  - 启用/关闭 Radio；
  - 事件通知类型下拉框；
  - 代理地址；
  - 代理端口；
  - 代理账号；
  - 代理密码；
  - “发送测试消息”按钮。

### 4.2 事件通知类型

首批事件范围：

- 登录；
- 修改密码；
- 任务执行结果；
- 添加下载器；
- 添加站点。

建议 UI 使用**多选下拉框**而不是单选。后端保存稳定事件枚举，例如：

- `AUTH_LOGIN_SUCCESS`
- `AUTH_PASSWORD_CHANGED`
- `TASK_EXECUTION_RESULT`
- `DOWNLOADER_CREATED`
- `SITE_CREATED`

后续可扩展 `VERSION_UPDATE_AVAILABLE`、`TASK_RECONCILE_REQUIRED` 等，而不修改渠道表结构。

### 4.3 聚合窗口的建议

用户界面可以删除“重复事件聚合窗口”，但建议**不要删除后端聚合保护能力**。站点故障、登录失败或任务批量完成都可能在短时间产生大量事件；服务端保留一个系统默认值，例如 300 秒，可以继续防止通知风暴。

也就是说：

- UI 不再让用户配置；
- 后端改为系统级固定默认值或高级内部设置；
- 数据库旧字段可以兼容保留，后续再做迁移收口。

### 4.4 任务基础链接地址的建议

删除用户配置后，通知中的任务链接可选择：

- 默认不附带绝对链接，只发送任务 ID/名称；或
- 后端根据受信任的系统 Public Base URL 自动生成。

不建议继续让每个渠道分别保存一个任意 URL。

### 4.5 代理配置

建议抽象为可复用的 `ProxyConfig`：

- enabled
- host
- port
- username
- password secret

站点和通知渠道都可以复用相同领域结构，但每个实例独立配置，避免把一个站点代理隐式共享给所有外部网络请求。

代理账号/密码读取 API 只返回 `proxy_credential_configured=true/false`，不回显明文。

### 4.6 发送测试消息

“发送测试消息”应支持两种场景：

- 新增表单尚未保存：使用临时凭证和临时代理发送一次固定测试消息，不持久化；
- 已保存渠道：使用 SecretStore 中的凭证发送测试消息。

测试消息正文固定且脱敏，不带任何真实任务/站点/账号数据。

## 5. 登录、头像与通知中心

### 5.1 登录页需求

登录从“仅密码”调整为“用户名 + 密码”。

计划增加 Docker 环境变量：

- `PACKBREAKER_ADMIN_USERNAME`
- `PACKBREAKER_ADMIN_PASSWORD`

### 5.2 管理员首次初始化与一次性临时密码

v0.1.6 固定采用以下初始化规则：

1. 用户名未配置时默认使用 `admin`；
2. 如果数据库中尚不存在管理员且提供了 `PACKBREAKER_ADMIN_PASSWORD`，该密码只作为首次 bootstrap 输入，数据库立即只保存 Argon2id 哈希；
3. 如果数据库中尚不存在管理员且没有提供 `PACKBREAKER_ADMIN_PASSWORD`，系统自动生成高强度、每个实例唯一的一次性临时密码，并设置 `must_change_password=true`；
4. 一次性临时密码只在首次成功创建管理员时输出一次，优先写入容器启动标准输出/错误输出，便于通过 `docker logs packbreaker` 查看；普通滚动业务日志、数据库日志、诊断导出、通知和 AI 上下文均不得保存或再次输出该明文密码；
5. 数据库已经存在管理员后，后续容器重启时环境变量不得覆盖数据库中的用户名/密码状态，尤其不能把用户在页面修改后的密码恢复成 bootstrap 密码。

未配置 Password 时不再依赖首次 Web 初始化页面。用户通过容器日志取得临时密码后登录；`must_change_password=true` 的账户只能进入修改密码流程，完成改密并重新认证后才能访问其他管理功能。

启动日志中的临时密码必须经过专用 bootstrap 输出路径，不能进入通用结构化日志 sink。其明文不进入 SecretStore、数据库或任何长期持久化字段；系统后续日志脱敏规则仍把该值视为 secret，防止异常路径再次输出。

### 5.3 管理员数据模型

当前 `administrator` 是固定 `id=admin` 的单管理员模型。v0.1.6 暂不需要升级为多用户系统，只需要增加：

- `username`
- `password_hash`
- `must_change_password`
- `password_changed_at`
- `last_login_at`

用户名建议唯一且首版不可在线修改，避免把“新增用户名字段”扩大为完整多用户权限系统。

### 5.4 右上角用户头像抽屉

主题、通知与退出登录统一移动到右上角用户入口。建议布局：

**顶栏**

- 圆形头像/默认字母头像；
- 用户名；
- 存在未读通知时头像右上角红点。

**点击后右侧抽屉**

- 用户名与当前版本简要信息；
- 主题：浅色 / 深色 / 跟随系统；
- 通知中心入口，存在未读时显示红点和未读数量；
- 修改密码；
- 退出登录。

### 5.5 修改密码页面

建议使用常规三字段流程：

- 当前密码；
- 新密码；
- 确认新密码。

规则：

- 校验当前密码；
- 新旧密码不可相同；
- 两次新密码必须一致；
- 使用现有密码强度/长度安全规则；
- 修改成功后撤销其他所有管理会话；
- 当前会话可选择立即重新登录，推荐直接注销并要求新密码重新认证；
- 生成 `AUTH_PASSWORD_CHANGED` 安全事件。

### 5.6 通知中心

头像红点需要一个独立于 Telegram/Server酱的**站内通知 Inbox**。首版通知类型：

- 修改密码记录；
- 登录记录；
- 版本更新记录。

建议新增 `user_notification` / `admin_notification` 持久化表：

- id
- event_type
- title
- message
- severity
- created_at
- read_at
- dedup_key

版本更新记录应以版本号做去重，例如同一个 `v0.1.7` 只创建一条“发现新版本”通知，不应每次后台检查都新增一条。

登录记录建议展示登录时间、结果和脱敏客户端信息；不应把密码、Cookie、完整 User-Agent 或敏感代理信息存入通知正文。

建议 API：

- `GET /notifications/inbox?unread_only=`
- `GET /notifications/inbox/unread-count`
- `POST /notifications/inbox/{id}/actions`：`mark_read`
- `POST /notifications/inbox/actions`：`mark_all_read`

## 6. AI 助手（AI Agent）

### 6.1 产品定位

系统设置新增顶层 Tab：**AI 助手**。

AI 助手的目标不是替代任务安全链，而是作为 PackBreaker 的运维与项目助手，帮助用户：

- 查询当前系统运行状态；
- 查询拆包任务/执行记录/失败原因；
- 查看项目版本和功能进度；
- 汇总日志和健康检查；
- 解释常见错误码；
- 根据系统已有证据给出排查建议；
- 通过支持双向通信的消息渠道进行对话。

### 6.2 v0.1.6 范围

首版固定为**只读 Agent**：可以读取和分析，但不直接执行以下动作：

- 新建/删除任务；
- 执行拆包；
- 添加/删除下载器任务；
- 修改站点/下载器配置；
- 修改密码；
- 删除 operation journal；
- 升级容器。

AI 可以生成“建议动作”并给出页面入口，但真正副作用仍由用户进入现有 UI 手动确认。

这样可以先解决“帮助用户处理当前项目问题、查看项目进度”的主要价值，同时避免 v0.1.6 同时引入一套新的高风险授权系统。

### 6.3 AI 助手 Tab

AI 助手 Tab 负责配置和状态管理，不提供 Web Chat。建议分成四个配置区：

#### A. 基础配置

- 启用 AI 助手；
- Provider 类型：`OpenAI` / `OpenAI-compatible`；
- API Base URL：OpenAI 可使用官方默认值，OpenAI-compatible 由用户填写；
- API Key（SecretStore）；
- Model：由用户自由填写字符串，不维护后端模型 allowlist/enum；
- 请求超时；
- 最大上下文范围；
- “测试连接”按钮。

OpenAI-compatible 的模型名称和 Base URL 不由 PackBreaker 预判可用性；“测试连接”使用用户当前填写的 Base URL、API Key、Model 发起最小请求，由真实 Provider 决定是否支持。这样 Provider 发布新模型后不需要等待 PackBreaker 后端更新枚举。

Base URL 只允许 HTTP(S)；优先使用 HTTPS。若用户明确选择 HTTP，应在 UI 中提示 API Key 与对话内容不会获得传输层加密，只适用于可信内网。Provider 请求不得在携带 API Key 时自动跨 Host 跟随重定向。修改 Base URL、API Key 或 Model 后，旧连接测试状态必须失效并回到 `UNTESTED`。

#### B. 数据权限

允许用户选择 AI 可读取的信息类型：

- 系统健康；
- 任务定义与执行记录；
- 脱敏运行日志；
- 站点连接状态；
- 下载器连接状态与运行指标；
- 当前版本/更新信息；
- 项目内置帮助文档。

无论用户如何选择，以下数据永远不能进入模型上下文：

- Cookie/API Key/密码；
- SecretStore 密文；
- CSRF/session token；
- operation journal 原始 secret/ownership payload；
- 不必要的绝对文件路径；
- 下载器密码和代理密码。

#### C. Telegram AI 对话

v0.1.6 **不提供 AI Web UI 对话**，Telegram 是唯一 AI 对话入口。通知渠道继续按能力区分：

- `SEND_NOTIFICATION`：可以发送通知；
- `RECEIVE_MESSAGE`：可以接收入站消息；
- `AI_CONVERSATION`：可以承载 AI 对话。

Server酱等单向渠道只保留通知能力；Telegram Bot 可以同时承担通知和 AI 对话，两项能力可分别启停。AI Tab 中配置 Telegram 渠道绑定、允许的 Chat ID / User ID、会话空闲超时和最大上下文消息数。

Telegram 入站首版优先使用 Long Polling，不要求用户暴露公网 Webhook。后台 Driver 持久化最后处理的 `update_id`，保证进程重启后不重复消费；Telegram/API 故障使用有限退避并与任务 Driver 隔离，不能影响拆包任务主链。

#### D. 会话与审计

- Telegram 会话元数据；
- Telegram Channel / Chat 绑定；
- 创建时间、最后消息时间；
- 会话空闲超时与上下文截断状态；
- AI 调用失败记录；
- 工具读取摘要。

不永久保存完整系统日志快照到聊天记录；会话只保存必要的 Telegram 用户消息、助手回复以及最小的“读取了哪些数据类型”审计摘要。模型上下文只带最近有界 N 条消息和本轮必要的脱敏 Tool 结果，不无限累积历史对话。

### 6.4 Agent 工具边界

建议定义一组明确的只读 Tool：

- `get_system_health`
- `get_version_status`
- `list_task_definitions`
- `get_task_execution`
- `query_redacted_logs`
- `get_site_status`
- `get_downloader_status`
- `search_help_docs`

Tool 不接受 Cookie、密码等秘密作为参数；AI 也不能调用任意 SQL、任意 Shell 或任意 URL。

如果后续版本需要让 AI 执行操作，必须复用现有 `TaskActionService`、CSRF、Idempotency-Key、operation journal 和人工确认，而不是为 AI 增加绕过现有安全门的“管理员后门”。

### 6.5 Telegram 对话鉴权与消息消费

Telegram 消息进入 AI Agent 前必须先验证“谁有权对话”。每个 AI Telegram 绑定配置允许的 Chat ID / User ID，并采用：

- Telegram Long Polling；
- sender/chat allowlist；
- 消息去重 ID；
- 持久化 `update_id` cursor；
- 每会话速率限制；
- 最大消息长度；
- 外部消息不能直接触发系统副作用。

未命中 allowlist 的消息不得调用 AI Provider，也不得调用任何 PackBreaker Tool。Telegram Chat/User ID 在普通日志中应使用摘要或最小化记录。AI Provider/Telegram 暂时不可用时只影响 AI 对话能力，不影响通知以外的 PackBreaker 核心运行。

## 12. 重点建议汇总

### 12.1 已确认并采用的设计原则

1. **站点地址改为后端固定 Registry。** 这不仅简化 UI，也能防止 Cookie/API Key 被发送到用户误填的第三方域名。
2. **新增/编辑弹窗的“测试连接”必须支持未保存配置。** 不应为了测试先创建一条垃圾记录再删除。
3. **站点详情按需获取，不在列表批量刷新。** 用户信息接口通常比普通 health 更重，也更容易触发限流。
4. **站点状态点至少四态。** 单纯绿色/红色不足以表达未测试、停用、限流/降级。
5. **通知聚合能力从 UI 隐藏，但后端继续保留。** 可以简化配置，同时不牺牲防通知风暴保护。
6. **用户名可以有默认值，密码不使用全局固定默认值。** 环境变量只负责首次 bootstrap；未配置密码时生成一次性随机临时密码并仅在容器首次启动日志输出，页面修改密码后数据库成为权威来源。
7. **通知红点要建立真正的站内 Inbox。** 不要用 Telegram/Server酱发送状态来反推 UI 红点。
8. **AI 助手 v0.1.6 先只读。** 先把“问状态、查日志、解释错误、看项目进度”做好，写操作以后再通过既有人工确认/幂等/journal 安全链逐项开放。
9. **通知渠道与 AI 对话渠道按 capability 区分。** v0.1.6 只通过 Telegram 与 AI 对话，不提供 Web AI Chat；单向通知 Provider 不应伪装成支持双向聊天。
10. **新站点按适配器验收状态逐个开放。** UI 枚举可以一次加入，但只有通过连接、搜索、详情、取种与真实只读测试的站点才标记为正式可用。

### 12.2 已冻结产品口径

- 下载器“当前文件总大小”固定表示**该下载器全部 Torrent 任务的内容总大小**。
- Cookie 与 API Key 站点都支持**实例级独立代理**。
- AI Provider 支持 OpenAI 官方 API 与用户自定义 OpenAI-compatible Base URL。
- AI Model 由用户自由填写，不由 PackBreaker 后端枚举限制。
- v0.1.6 不提供 AI Web Chat，Telegram 是唯一 AI 对话入口。
- 未配置管理员 Password 时自动生成每实例唯一的一次性临时密码，仅首次 bootstrap 时输出到容器启动日志，并强制首次登录修改。

仍需要凭真实站点资料/凭证在实施阶段确认的是适配器事实，而不是产品决策：`Rousi Pro` 的正式内部枚举/官方标识，以及各新增站点的固定 URL、凭证类型、API/NexusPHP 变体和具体字段映射。

## 13. v0.1.6 完成定义

v0.1.6 只有在以下条件同时满足时才视为完成：

- 下载器页面完成 UI 简化、未保存测试连接和真实运行指标。
- 新站点类型进入 Registry；声明“正式支持”的站点均通过对应 Adapter 与真实只读验收。
- 站点卡片状态、用户详情、超时/搜索间隔/User-Agent/代理配置真实生效。
- 通知渠道能够按事件订阅、使用代理、测试发送，敏感参数不回显。
- 用户名+密码登录、一次性临时密码 bootstrap、首次强制改密、头像抽屉和站内通知完整工作，重启后密码不会被环境变量意外覆盖。
- 登录/修改密码/版本更新能够形成可读、可标记已读的站内通知。
- AI 助手能够使用 OpenAI 或 OpenAI-compatible 自定义 Base URL，Model 可由用户自由填写并通过真实 Provider Probe 验证。
- Telegram Long Polling 能够与 AI 完成有界多轮对话，未授权 Chat/User 无法读取任何 PackBreaker 信息，重启后不会重复消费已处理 update。
- AI 至少完成一组只读系统工具调用，且敏感数据不会进入模型上下文；系统中不存在 Web AI Chat 页面或 AI 直接执行拆包/配置修改/升级等副作用的入口。
- “关于”页面展示当前版本、项目说明和 GitHub 地址。
- v0.1.5 数据库可升级，现有任务/下载器/站点配置不丢失。
- 后端、前端、OpenAPI、浏览器 E2E、仓库安全扫描和真实环境验收全部通过。
