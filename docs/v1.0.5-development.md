# PackBreaker v1.0.5 研发设计与验收文档

## 1. 版本目标

v1.0.5 以 v1.0.4 正式发布基线为升级输入，聚焦三项产品变化：

1. **解除候选站点的正式任务门禁。** 当前已内置适配器的全部站点类型均可配置、启用并直接参与拆包流程，不再因为历史 `PENDING_REAL_VALIDATION` / `PENDING_ADAPTER` 标记被运行时拒绝。
2. **接入 easychen/CookieCloud。** 在系统设置提供 CookieCloud 配置、连接测试、立即同步与周期自动同步，将服务端 Cookie 安全同步到 PackBreaker 已配置站点。
3. **取消下载器路径必须位于 `/data` 的限制。** 下载器路径映射可指向 PackBreaker 容器中任意管理员显式挂载的绝对目录，例如 `/downloads`、`/downloads2`、`/mnt/media`；配置的映射目录自身成为授权边界。

本版本不降低凭据校验、同源限制、路径逃逸防护、硬链接诊断、执行计划、审批、journal 或回滚安全门。

## 2. 站点开放设计

### 2.1 产品语义

- `CONFIGURABLE_SITE_KINDS` 与 `PERSISTED_SITE_KINDS` 覆盖当前全部 `SiteKind`。
- 历史“尚未真实验收”状态仅保留为研发/发布证据，不再作为生产任务运行时门禁。
- 创建站点后仍默认停用；用户显式启用后可进入 `enabled_adapters()` 与任务执行链。
- 启用仍要求对应主凭据存在；Rousi Pro 额外要求独立下载 Cookie。
- 真实连接失败、身份不匹配、凭据类型不匹配、固定来源地址不匹配等错误继续失败关闭。

### 2.2 Rousi Pro 双凭据

Rousi Pro 的主凭据始终为 API Key，用于搜索/API 请求；下载 Cookie 是独立秘密，只用于 torrent 下载接口。任何 CookieCloud 同步都不得覆盖 API Key。

### 2.3 验收

- 全部站点类型可保存、启用并进入正式 Adapter Registry。
- 缺失凭据或损坏的导入配置仍不能进入任务链。
- 旧候选验收脚本不再依赖 PENDING 状态判断，但仍保持显式 `--live` / acknowledgement 门禁。

## 3. CookieCloud 设计

### 3.1 对接项目与协议

本版本唯一对接目标是 **easychen/CookieCloud**：

- 项目：`https://github.com/easychen/CookieCloud`
- PackBreaker 请求：`GET {server_url}/get/{uuid}`
- UUID 作为路径参数发送。
- CookieCloud 密码**不发送给服务器**，只在 PackBreaker 本地用于解密返回密文。
- 支持 easychen/CookieCloud 的 legacy CryptoJS/OpenSSL 兼容格式与 `aes-128-cbc-fixed`。
- 密码由 PackBreaker `SecretStore` 以应用现有加密机制保存；API 与日志只返回 `password_configured`，不得回显密码、密文或 Cookie 明文。

### 3.2 配置模型

单例 `cookiecloud_setting/default` 保存：

- `enabled`
- `server_url`
- `uuid`
- `password_secret_id`
- `auto_sync`
- `sync_interval_minutes`
- `request_timeout_seconds`
- 最近连接测试、最近同步状态/时间/错误码
- 最近匹配站点、更新站点、未匹配域名统计
- 乐观锁 `version`

配置写入使用强 ETag / `If-Match`。密码操作明确区分 `KEEP`、`SET`、`CLEAR`。

### 3.3 API

- `GET /api/v1/cookiecloud/config`
- `PUT /api/v1/cookiecloud/config`
- `POST /api/v1/cookiecloud/test`
- `POST /api/v1/cookiecloud/sync`

读操作要求管理员会话；写、测试与同步要求管理员会话 + CSRF。所有响应均不得包含 CookieCloud 密码或站点 Cookie 明文。

### 3.4 域名匹配

- Cookie 的 domain 采用 host 边界匹配，允许 `.example.com` 匹配 `pt.example.com`，不得把 `badexample.com` 误判为子域。
- 过期 Cookie 不参与同步。
- 只更新 PackBreaker 当前已配置且凭据类型兼容的站点。
- Cookie 站点更新主 Cookie。
- Rousi Pro 只更新 `SITE_DOWNLOAD_COOKIE`。
- 未匹配 Cookie 域只计数，不自动创建站点。
- Cookie 内容未变化时不递增站点配置版本，避免无意义失效执行快照。

### 3.5 自动同步

`CookieCloudDriver` 使用短周期 tick 读取持久配置，真正的同步周期由 `sync_interval_minutes` 决定：

- 未启用 CookieCloud：跳过。
- `auto_sync=false`：跳过。
- 距离最近同步尚未到期：跳过。
- 到期：执行一次与手动同步相同的安全同步。
- 同步失败只记录 CookieCloud 状态并写应用日志，不得使 FastAPI 主服务退出。

## 4. 下载器任意挂载路径设计

### 4.1 原问题

v1.0.4 及以前把 `PACKBREAKER_DATA_DIR`（默认 `/data`）同时当作：

1. 目录来源/输出目录的数据根；
2. 下载器远程路径映射的唯一容器授权根。

因此即使用户已经把宿主机目录正确挂载成 `/downloads:/downloads`，下载器配置仍会要求额外映射到 `/data/downloads`。

v1.0.5 将两者解耦。**目录来源和普通输出目录仍使用 `PACKBREAKER_DATA_DIR`；下载器来源则以该下载器显式配置的 `container_prefix` 为授权根。**

### 4.2 新规则

合法示例：

| 下载器看到的路径 | PackBreaker 容器中实际路径 |
| --- | --- |
| `/downloads` | `/downloads` |
| `/downloads2` | `/downloads2` |
| `/volume/media` | `/mnt/media` |
| `D:\Downloads` | `/mnt/windows-downloads` |

约束：

- `container_prefix` 必须是容器内绝对路径。
- 禁止直接把容器根 `/` 作为映射根。
- 远程路径只允许映射到命中的 `container_prefix` 内，不能通过 `..` 或解析后的路径逃逸。
- 任务物化后，如果来源位于 `PACKBREAKER_DATA_DIR` 内，继续保存兼容的相对 `source_root`；如果来源位于其外，则冻结规范化绝对路径。
- 后续 Analyze、preflight currentity、人工映射复验、execution plan 等每次重新读取绝对 `source_root` 时，都必须重新根据该任务绑定下载器的路径映射授权。
- 未映射绝对目录、容器根、符号链接逃逸或丢失下载器配置均失败关闭。
- 删除仍被任务引用的下载器继续被禁止，因此任务的授权来源不会静默丢失。

### 4.3 硬链接边界

取消 `/data` 强制**不等于保证任意两个挂载都能硬链接**。保存/启用前仍必须使用路径诊断验证：

- 源文件真实可见、普通文件、可读；
- 目标目录真实存在、可写；
- 正反向映射一致；
- source/target `st_dev` 一致；
- 实际创建并清理一次临时 hardlink 成功。

目录来源和默认输出目录仍以 `PACKBREAKER_DATA_DIR` 为管理根。如果下载器来源位于其它 mount，而输出位于 `/data`，是否能硬链接以真实诊断结果为准；不得根据宿主路径名称推断。

## 5. 前端设计

系统设置新增 `CookieCloud` Tab：

- 启用开关
- Server URL
- UUID
- 密码（已配置时留空表示 KEEP）
- 自动同步
- 同步间隔
- 请求超时
- 连接状态 / 最近测试
- 同步状态 / 最近同步
- 匹配、更新、未匹配统计
- “测试连接”“立即同步”“保存配置”

HTTP Server URL 可配置，但 UI 必须明确提示仅建议受信内网；公网优先 HTTPS。

下载器路径映射表单：

- 不再预设 `/data/downloads`。
- 默认示例可使用 `/downloads → /downloads`。
- 右侧说明为“PackBreaker 容器内实际挂载路径”，可为 `/downloads`、`/mnt/media` 等。
- 前端直接拒绝相对容器路径和 `/`；最终安全判断以后端为准。

## 6. 数据库迁移

新增 Alembic revision：

`0031_site_type_capacity_v101 → 0032_cookiecloud_v105`

迁移仅新增 CookieCloud 配置表及约束，不重建或改写现有站点、下载器和任务数据。

升级验收必须至少证明：

- v1.0.4 数据库可直接升级到 head；
- 现有站点类型、地址、启用状态、版本保持不变；
- `PRAGMA foreign_key_check` 为空；
- 新 CookieCloud 表存在且首次升级不擅自生成带凭据配置。

## 7. 安全要求

- 不提交或记录真实 Cookie、API Key、CookieCloud 密码。
- CookieCloud 请求 URL 不包含密码。
- 错误响应不得包含远端密文、Cookie 明文或密码。
- 自动同步不得改变站点 enabled 状态。
- 路径映射开放后不得把 `/` 变成授权根。
- 下载器来源绝对路径必须与任务绑定下载器建立可证明的映射关系。
- 所有原执行计划、审核、journal、幂等和高风险授权规则保持不变。

## 8. 测试与验收计划

### Stage A：站点开放

- 全 SiteKind 配置/持久化/启用单元测试。
- 正式 adapter registry 测试。
- Rousi Pro 双凭据测试。
- 历史候选只读验收脚本更新。

### Stage B：CookieCloud 核心

- URL/UUID 规范化。
- legacy 与 aes-128-cbc-fixed 解密。
- 错误密文/密码失败关闭。
- domain 边界匹配、过期过滤、Cookie header 生成。
- API 密码不回显、SecretStore 加密持久化。

### Stage C：CookieCloud 同步

- Cookie 站点主 Cookie 更新。
- Rousi Pro API Key 保留、下载 Cookie 更新。
- 重复同步幂等。
- 自动同步 Driver 到期/未到期/禁用分支。
- 本机真实 HTTP easychen 协议等价服务验收。

### Stage D：任意下载器挂载

- `/data` 外路径映射保存。
- 实际文件路径诊断。
- 根目录 `/` 拒绝。
- 未映射绝对路径拒绝。
- 下载器来源任务在 `/data` 外物化、Analyze 与重试链保持授权。
- 旧 `/data` 映射兼容。

### Stage E：完整回归

必须通过：

```bash
python scripts/check.py
python scripts/test.py
```

并完成前端生产构建、OpenAPI 类型一致性和 v1.0.4 → v1.0.5 数据库迁移回归。

- 真实外部 CookieCloud 服务验收：已提供受控只读脚本 `scripts/check_cookiecloud_readonly.py`；当前尚未提供专用验收配置。脚本只执行 GET + 本地解密，不打开 PackBreaker 数据库、不修改站点 Cookie；不得把真实凭据提交到仓库。

真实验收配置仅放在忽略跟踪的 `runtime/cookiecloud-acceptance.secret`，文件权限必须为 `0600`，JSON 仅包含 `server_url`、`uuid`、`password`，可选 `timeout_seconds`。执行时必须显式确认：

```bash
python scripts/check_cookiecloud_readonly.py --live --acknowledge-cookie-read
```

成功输出只包含加密格式、域名/Cookie 数量和更新时间是否存在，不输出域名列表、Cookie 明文、UUID、密码或远端密文。

本文件是 v1.0.5 后续开发、评审与发布验收的版本基线；实现与本文冲突时，必须先更新设计与测试再改变行为。
