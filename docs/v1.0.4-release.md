## 正式发布与受控恢复

- 候选分支在正式发布前已经通过 v1.0.3 → v1.0.4 的 AMD64/原生 ARM64 Web updater、失败自动回滚、匿名 `/data` 卷恢复回归、隔离真实 qBittorrent/Transmission API 与完整质量门禁。
- 原始 Release run [#36668291164](https://github.com/YYxiaoma/PackBreaker/actions/runs/36668291164) 成功完成 Tag/基线检查、全量质量门禁、候选相邻升级/回滚、正式多架构镜像推送、平台身份检查、已发布 AMD64 运行、相邻升级/回滚及 Web updater；随后在同一 AMD64 Runner 的 QEMU ARM64 已发布镜像运行步骤失败，日志为 `cannot overwrite digest sha256:3d1dd66...`。原始 run 保留 Failure 状态，后续原生 ARM64 与 Release 资产 Job 因依赖关系被跳过。
- 受控恢复 run [#36669688184](https://github.com/YYxiaoma/PackBreaker/actions/runs/36669688184) 固定并复核**同一已发布 digest**，在三个独立 Runner 上分别完成 AMD64、隔离 QEMU ARM64 与原生 ARM64 运行；AMD64/ARM64 正式 Web updater、失败回滚以及原生 ARM64 匿名卷保留检查均成功。
- 恢复的资产 Job 再次核对 Tag、上一正式 Release、上一基线、v1.0.4 version digest 与 `stable/latest` 旧 digest 后，才从不变镜像生成 SBOM/Release manifest/checksum，发布 GitHub Release，下载回读三份资产，最后把 `stable/latest` 推进到同一 v1.0.4 digest。
- 发布后流水线已改为把 QEMU ARM64 已发布镜像验证放到独立 Runner，避免未来在同一个经典 Docker image store 中先加载 AMD64、再以同一 index digest 拉取 ARM64 所产生的本地 digest 冲突；正式资产继续同时等待 QEMU ARM64 与原生 ARM64 两个独立 Job。

## 本版能力与部署边界

- Web updater 的容器替换计划现在会从 Docker inspect 的实际 `Mounts` 中恢复未在 `HostConfig.Binds/Mounts` 显式声明的 Docker Volume 身份，保留原卷名称与只读状态；无法安全识别的额外挂载失败关闭，不能静默换成新空卷。
- 该修复只存在于 v1.0.4 及后续程序。**由 v1.0.3 自身发起升级时仍执行 v1.0.3 的旧 helper**，因此 v1.0.3 容器若依赖 Compose 未声明的匿名 `/data`，不能把直接 Web 升级视为已证明安全；应先受控固定原卷或由宿主机完成一次升级。以 v1.0.4 及后续作为升级源时，匿名卷恢复才进入正式代码路径。
- v1.0.3 已加入的 docker.sock 数字组保留继续生效；不会为方便而 chmod/chown 宿主机 socket，也不会常驻 root 来绕过权限问题。
- 八个新增站点仍为 `PENDING_REAL_VALIDATION`，只开放加密配置与只读连接能力，生产辅种任务门禁没有因本次发布扩大。

## 下版升级基线

发布后 `release-baseline.json` 固定本次 v1.0.4 Tag、源码提交、不可变 OCI Index、数据库 revision 与成功恢复 run `36669688184`。后续候选必须以 v1.0.4 作为上一正式版本重新完成跨版本升级、失败回滚、双架构运行和 Web updater 门禁；同版本替换不能冒充跨版本升级证据。
