## Synology 挂载证据与仅只读站点验收授权（2026-09-20）

- 用户提供的 Synology Container Manager 图形界面部署的 `docker inspect` 证据：原下载目录分别挂载在容器内 `/downloads` 和 `/downloads2`；另有独立 Docker 卷挂载 `/data`，配置挂载在 `/config`。目录只读检查显示 `/data`、`/downloads`、`/downloads2` 存在，但 `/data/downloads` 和 `/data/downloads2` 不存在。故原有安全根限制下，将 `/downloads` 当作 **container_prefix** 会被拒绝；仅调整前端默认映射不能在尚未增加新挂载的 Synology 容器上消除该报错。
- 用户询问是否可将下载器路径设为不受 `/data` 限制：当前版本不做无条件放开。由用户在生产端保留原有 `/config` 和 `/data` 卷身份、额外挂载两路数据到 `/data` 子目录，是本次低风险部署方案；若要支持多根，须独立设计跨任务阶段及安全网关的一致策略与回归矩阵，不能将单点校验删除当作修复。操作前只读检查原卷身份、同名目录冲突及跨挂载硬链接风险；详情见 `docs/deployment.md`。
- 用户已授权使用现有 M-TEAM、HDTime、HHClub 凭据仅验收用户资料及必要只读接口，凭据有效性未知；**该授权不包括主动搜索种子、下载种子、修改真实下载器或生产数据库**。当前研发 Runner 为 `/workspace/PackBreaker`，无 Synology `/volume*`、`/data`、`/downloads`、Docker socket，因此不能代表 Synology 实际运行实例，亦尚未访问上述三个真实站点。验收应使用与生产实例对应的经认证只读 `GET /api/v1/sites/{site_id}/profile` 或受控只读适配器请求，任何报告只输出站点名、成功/失败状态和字段有值/缺值状态，绝不保存 Cookie、API Key、UID、用户名或第三方原始响应。`POST /sites/{site_id}/test` 会更新连接状态证据，不应在本次仅只读授权下调用。
