# PackBreaker v1.0.1 研发记录（未正式发布）

## 2026-09-22 范围变更（取代下述旧的站点用户详情目标）

- **取消站点用户详情查看**：不再展示用户等级、做种量、魔力值、做种积分、做种/发种数等独立详情；撤销前端详情入口和资料缓存，并移除公开的 `GET /api/v1/sites/{site_id}/profile` 子资源。此处的「详情」专指站点**用户资料**，不能误删辅种所需的 torrent 详情、搜索、文件列表和完整校验。
- 新增目标为 HDHome、KeepFrds、UBits、HDFans、Rousi Pro、BTSCHOOL、PTTime、聆音Club 共八个站点的认证、同源连接、受控搜索、候选解析及拆包任务集成。旧版 M-TEAM、HDTime、HHClub 的搜索/下载和执行安全边界保持不变。
- 用户已将八站点配置放在本地忽略追踪的 `runtime/site-acceptance.secret`；检查确认 JSON 结构有效、权限 `0600`，八项均有 Cookie，且文件未被 Git 跟踪。不得复制凭证至仓库、测试、日志或聊天。文件中站点名称 `BTSchool` / `PTTime` 与产品展示命名大小写不同，不代表缺少配置。
- 已有七个 Cookie 待适配类型及新注册的聆音Club、Rousi Pro 均保持 `PENDING_ADAPTER`，严禁仅凭凭据已配置就放开保存、测试或生产任务；聆音Club 的固定 HTTPS 域名已与站点公开页面和用户本地配置核对。Rousi Pro Registry 指定 `API_KEY`，其后用户已在本地验收文件补充独立 API Key（保留 Cookie），不得把 Cookie 当 API Key 发送。
- **Passkey 不作为全站必填项**：仅在逐站核对已审查的认证、搜索、取种接口后，才确定是否需要独立字段；已有 torrent 的 Tracker 参数不得改写，下载令牌不得记录/隐式重试。仅提供 Cookie 不足以证明 Passkey 永远不需要。
- Rousi Pro 需要单独调查：第三方项目 [AMMDS 适配文档](https://ammds.lifebus.top/en/docs/v1.6.58/plugin/siteSearch/Rousi/) 将其 API 鉴权字段命名为 `PassKey`（API Key），[MoviePilot 插件讨论](https://github.com/jxxghp/MoviePilot-Plugins/issues/1067) 还提及 Bearer Token；均非本项目对搜索/下载接口的真实验证，不能据此把当前用户提供的 Cookie 自动冒充 API Key，亦不能把该 API 字段与 Tracker Passkey 自动视作同一凭证。
- 当前已获准在固定可信域名上执行最小只读认证和搜索检查；种子文件下载、下载器写操作和生产部署尚未执行且应分开审批/验收，不能将离线模拟结果描述为真实端到端成功。

原有用户资料适配、字段截图与失败分析仅作为历史研发记录，不再构成当前 v1.0.1 发布退出门槛。

## v1.0.1 新增站点分级验收门槛（取代逐站重复完整真实辅种的要求）

本轮确认：**每站独立验收必做、每类协议统一分析集成验收必做、真实完整拆包辅种任务按代表性场景执行**。新增站点不是只凭一次取种成功即可开放生产，也不要求每站无条件重复破坏性或高风险的真实任务。

1. **逐站独立验收：** 八站分别核对站点认证、固定同源、搜索与分页、候选字段、详情/下载认证、Passkey/令牌来源、至少一个真实 Torrent 文件元信息及异常失败关闭。已完成的真实取种记录仅是单一样本，不等于完整辅种；不能使用一站的凭据或结果替代另一站。
2. **按协议组隔离集成：** NexusPHP Cookie 组覆盖七站各自的真实候选适配器，通过 MockTransport 的合成 HTML/种子与临时源媒体、临时 SQLite，将实际 `SiteAdapterFactory` → `AnalysisService` → 搜索 → torrent 详情 → 下载 → bencode 解析 → 文件映射/完整校验 → 不可变 preflight 串通；PTTime 的由站点提供的 Passkey 下载链接另作合成断言。Rousi Pro 采用独立 API Key 搜索与 Cookie 取种的隔离适配器；默认工厂没有 Cookie 时保持 `SITE_ADAPTER_PENDING`。只有明确注入隔离候选 Cookie 且搜索候选标识、标题和大小校验通过后，才允许使用经验证的搜索元数据代替独立详情请求，且仍须完成真实 Torrent 元信息、文件映射及完整内容校验。
3. **代表性真实端到端：** 在隔离目录和受控测试下载器中，选择普通 NexusPHP Cookie、小文件与大目录/Passkey 场景，验证执行计划、风险审批、文件链接隔离、客户端校验、辅种与回滚；Rousi Pro 的正式双凭据管理、候选元数据充分性与下载权限等发布门禁通过后，需补充覆盖其特有认证路径的代表性场景。若站点存在差异化执行逻辑、失败模式或凭据处理，必须针对该差异补测，不得借复用理由跳过。每一项测试需有明示的安全授权与可审查证据，**不得**在正式下载器或真实媒体目录上直接批量执行。

### 本轮新增的隔离集成测试证据

- `tests/application/test_analysis.py` 新增七站参数化测试，直接使用真正的 NexusPHP 候选适配器、`SiteAdapterFactory` 与 `AnalysisService`，从合成搜索页面与详情页读取固定同源链接和合成 Torrent，映射到临时源文件并取得 `FULL_VERIFIED` preflight；PTTime 额外断言站点提供的模拟 Passkey 保持在下载链接中，未进入日志。原有站点路径不变。
- 新增 Rousi Pro 的**失败关闭**集成场景：使用真正的候选工厂和统一分析服务，从合成 API 搜索获取候选，确认 `fetch_details()` 尚未实现时 preflight 记录 `SITE_ADAPTER_PENDING`，没有发起种子下载、没有误标 `FULL_VERIFIED`。这清楚暴露仍需完成的协议差异，而非绕过详情或使用测试替身冒充集成成功。
- **后续推进的隔离候选分析通路：** 仅明确传入下载 Cookie 的 Rousi Pro 候选适配器，将已校验的 API 搜索标题、远程正整数 ID 与大于零的大小视作足够的候选匹配元数据，避免猜测尚未验证的额外详情 API；没有 Cookie 的默认工厂仍走原来的 `SITE_ADAPTER_PENDING` 路径。此路径每次分析最多挑选一个候选获取 Torrent，真正的 `AnalysisService` 继续执行 bencode 解析、本地映射及逐片哈希校验，搜索标题/大小**不可能单独产生 `FULL_VERIFIED`**。新合成集成用例分别证明有效 Torrent 得到 `FULL_VERIFIED`、损坏的 Torrent 被标记 `SITE_INVALID_RESPONSE` 且无完整校验证据；搜索大小缺失、大小为零、种子 ID 越界也会在下载前失败关闭。以上均不是 Rousi Pro 的真实分析或正式凭据管理通过证据；未验证的独立 `fetch_details()` 方法继续保持 `SITE_ADAPTER_PENDING`。
- 所有新增测试仅使用 MockTransport、合成凭据、合成 torrent、临时源文件和临时 SQLite；不加载 `runtime/site-acceptance.secret`，不访问真实站点、下载器、Tracker 或正式媒体。**模拟集成通过不代表真实端到端通过，也不改变八站 `PENDING_ADAPTER` 门禁。**

### Rousi Pro 双凭据独立存储基础（尚未开放配置）

- 已新增兼容迁移 `0030_site_download_credential_v101`：向现有 `site` 表增加一个可空的 `download_secret_id` 引用槽位，**不复制、覆盖现有 API Key 或 Cookie，也不写入明文、JSON capabilities、日志或前端**。独立下载 Cookie 仍通过已有 `SecretStore` 的 `SITE_DOWNLOAD_COOKIE` 加密记录保存；迁移本身不会自动写入任何站点的下载 Cookie。
- 为避免 SQLite 对含下游任务外键的 `site` 父表进行危险的批量重建，本阶段只增加可空列，和现有 `proxy_secret_id` 一样由应用负责关联记录生命周期；站点删除时同步清理独立密文，现有主凭据替换、清除或站点类型切换时也清除历史下载密文，避免跨身份沿用；`set_enabled` 进一步检查站点类型必须属于正式支持集。
- **发现并保留正式接入前的重要阻塞：** 现有数据库 `ck_site_type` 仅允许 M-TEAM、HDTime 和 HHClub，`SiteService.create()` 也只允许这三类正式站点；Rousi Pro 当前无法、也不应该在正式站点表中创建记录。没有为让候选测试通过而放宽旧表约束或伪造真实 Rousi 配置；后续须独立设计、回归验证对旧数据库及下游外键安全的类型扩展迁移，再接入具备 CSRF/权限校验、脱敏响应和版本冲突保护的双凭据 API/UI，以及仅在正式放行后才加载 Cookie 的生产适配器。
- 隔离测试使用**现有受支持的合成 HHClub 行**验证可空列、独立加密、主/次密文分离、主凭据轮换与站点删除清理；另从旧 `0029` 数据库携带合成已有站点升级至 `0030`，核对记录及版本保持不变、次凭据为 `NULL`，并验证 Rousi Pro 公共创建入口仍返回 `SITE_ADAPTER_PENDING`。这些只证明基础存储向后兼容，**不是 Rousi Pro 正式双凭据配置已完成或生产任务可用的证据**。

### 站点类型扩展前置：历史任务关联迁移保护

- 在隔离 SQLite 中证明了危险情形：对 `site` 父表执行直接 `CREATE/INSERT/DROP/RENAME` 重建，即使设置 `PRAGMA defer_foreign_keys=ON`，`task_definition.site_id` 也可能因 `ON DELETE SET NULL` 变为 `NULL`，而 `PRAGMA foreign_key_check` **仍然通过**。因此单纯的批量重建和外键一致性检查，不足以作为新增站点类型的安全迁移证据。
- 在 `upgrade_database_safely` 原有的实例锁、升级前备份、临时副本迁移及原子切换机制中加入关系指纹门禁：如升级前已存在 `site` / `task_definition` 表，则分别按源库当时已有列，以只读、流式 SHA-256 摘要比较旧站点 ID、类型、主密文引用、版本及已有任务 ID → site ID 关联。只比较这些结构性字段，**不读取或解密 Cookie、API Key、媒体路径及种子内容**；历史版本缺少某表或新字段时不将新增表/字段误报为数据丢失。候选副本若删除站点、变更历史站点身份或清空任务关联，直接拒绝切换现有数据库，保留升级前快照供排查。
- `tests/integration/test_site_upgrade_relation_guard.py` 使用带有旧版站点和关联任务的临时 `0029` SQLite 证明正常升级保留原数据；模拟实际迁移后的任务关联清空、站点类型被改写（这两种异常均可能通过普通 FK 检查），核对升级流程拒绝替换原库，原数据库及 Alembic revision 均保持不变。历史版本升级矩阵也已纳入回归。
- **本轮仍未放宽 `ck_site_type`、未创建新站点记录，也未新增生产配置/启用入口。** 后续真正的约束扩展迁移还须独立验证能完整保留旧站点主表、索引、任务外键、密文引用、升级失败恢复及候选副本的一致性检查；不能把此防护门禁写成“八站正式持久化已开放”。

### 站点类型容量迁移 0031：允许存储、仍禁止候选站点生产启用

- 新增迁移 `0031_site_type_capacity_v101`，将数据库 CHECK 所允许的类型扩展至固定 Registry 中的 11 种站点（原有 3 种加新增 8 种）。`DATABASE_SITE_KINDS` 与应用层 `PERSISTED_SITE_KINDS` **明确分离**：数据库的类型容量变化不改变 `SiteService.create/update/set_enabled`、站点 Profile、运行时适配器工厂的候选站点阻断逻辑。八个新增站点依然 `PENDING_ADAPTER`，且本次没有新增正式配置 API/UI 或连接任何生产凭据。
- SQLite 的 `PRAGMA foreign_keys=OFF` 必须在事务开始前切换，事务内再设置无效；因此本迁移使用 Alembic 显式 autocommit 边界，在确认外键检查确实关闭后才批量重建 `site`，复制原有列及约束、索引，验证 `foreign_key_check` 和关键索引，再恢复外键检查并校验恢复成功。运行时的 `upgrade_database_safely` 仍先制作安全备份，只在独立临时副本中执行迁移；升级前后的历史站点身份及任务关联指纹不一致则拒绝原子切换。**不允许在运行中的真实库手工执行此重建。**
- 通过携带原有站点、合成加密引用、关联任务的旧 `0029` 数据库升级测试，验证历史站点及任务关联、站点名称唯一性、站点到密文的 FK、任务到站点的 FK、`ix_site_type_enabled` 索引、`integrity_check` 与 `foreign_key_check` 均保留；隔离数据库可接受八种新增类型并拒绝未知类型，正式创建入口仍按 `SITE_ADAPTER_PENDING` 拒绝。正常升级不代表 Rousi Pro 正式双凭据配置或真实辅种任务已通过。
- `0031` 的 Alembic `downgrade` 故意不重建父表、不删除可能存在的候选行；要恢复旧应用版本，应使用升级前创建的完整数据库安全备份与匹配的旧镜像，不得把仅回退 Alembic revision 当成完整应用回滚。正式放行前仍需独立完成双凭据 API/UI、对应鉴权及隔离集成、代表性受控真实端到端验收。
- 另补充生产侧防御：即使有人绕过正式 API，直接向已扩容数据库导入 `enabled=1` 的 Rousi Pro 候选记录，`SiteService.enabled_adapters()` 及 `enabled_site_versions()` 仍在创建适配器、读取凭据或派发任务前按正式白名单返回 `SITE_ADAPTER_PENDING`。合成数据库测试覆盖该情况；**不能**以数据库可以存储候选类型为由绕过任务授权门禁。

### 双凭据正式配置前置：候选站点历史导入与 API 失败关闭

- 检查现有站点 API/SecretStore 后，明确保留仓库安全约束：`PENDING_ADAPTER` 类型不能经由正式配置 API 创建站点、生成主/次密文或执行真实连接测试。这一阶段尚未开放 Rousi Pro 下载 Cookie 的保存接口；下述后续阶段虽已接入受正式支持门禁保护的 API 和前端代码，但仍未对真实 Rousi Pro 开放。
- 增强 `SiteService._connection_snapshot()`：对直接导入或遗留的候选站点，在读取主凭据前阻断已保存站点的连接测试与用户资料请求；`enabled_adapters()` 则先检查整批已启用类型均已列入正式白名单，**再**解密任一站点凭据，防止“受支持站点在前、非法候选在后”时发生部分密文读取和部分适配器创建。
- 新增独立合成数据库和受鉴权 API 测试：即使人为导入含合成 API Key 的 Rousi Pro 行，`/sites/{id}/test`、`refresh_capabilities`、`enable`、批量启用适配器、独立连接测试及用户资料调用都返回 `SITE_ADAPTER_PENDING`，不访问外网、不读取合成密文、不更改站点版本，也不在响应中回显凭据。已有受支持站点的正常配置与凭据轮换逻辑不变。
- 双凭据正式开放仍须满足逐站/协议组/代表性受控 E2E 的发布门槛；下载 Cookie 不得存于 `capabilities`、代理密码或主 API Key 中。具体配置与凭据生命周期实现及测试见下节。

### Rousi Pro 双凭据配置 API / 前端联动（候选代码已完成，正式支持仍关闭）

- 在 `SiteService`、`SiteAdapterFactory`、`SiteView`、受管理员登录及 CSRF 保护的 `/api/v1/sites` 创建/编辑/临时只读测试接口中，新增**独立的下载 Cookie**：主凭据保持 API Key，Cookie 写入类型为 `SITE_DOWNLOAD_COOKIE` 的独立 `SecretStore` 加密记录，仅保存 `download_secret_id` 引用；公共响应只返回 `download_credential_configured` 布尔值，不返回明文、密文或密文 ID。更新操作继续要求强 `If-Match`；替换主 API Key 会清除旧 Cookie，替换或显式清除 Cookie 则停用站点并重置连接状态、清理旧密文。
- `SiteAdapterFactory` 仅允许 Rousi Pro 获得额外 Cookie，普通 Cookie/API Key 站点携带第二凭据会被拒绝。下载 Cookie 仅随固定同源取种接口发送，API Key 仍只随只读认证与搜索请求发送；Rousi Pro 缺少下载 Cookie 不允许启用。只读临时表单测试必须明确提供当次 Cookie，不允许默默复用已保存的旧密文。
- 前端站点表单增加独立密码输入框及清除选项，站点卡片只显示下载 Cookie 配置状态；API Key 轮换且未同时提交新 Cookie 时给出提示。更新了 `frontend/openapi.json` 和由其生成的 `frontend/src/api/generated/schema.ts`；原有站点与配置字段继续兼容。
- 为不违背 `PENDING_ADAPTER` 约束，**正式 Rousi Pro 的保存、测试和启用入口仍被禁用，且不能落盘真实凭据或发起网络请求**。新 API 全链路测试只在临时数据库中用 `monkeypatch` 为单个合成 Rousi 站点临时模拟“已批准正式支持”，验证两种密文隔离、HTTP 响应脱敏、并发版本冲突、Cookie 轮换与旧密文删除、主 API Key 轮换联动清理、缺 Cookie 拒绝启用，以及合成 Torrent 固定同源 Cookie-only 下载。另验证真实 `PENDING_ADAPTER` 门禁在同时提交 API Key 与 Cookie 时仍拒绝创建/临时测试，且未产生密文。
- 以上只代表**正式接入所需的配置功能已在候选代码中备齐**，不代表站点适配与代表性真实拆包辅种任务已完成，亦不代表可直接提升 `PERSISTED_SITE_KINDS` 或发布。

### 六站首次只读认证探测

### 七站受限真实搜索和字段修复

## NexusPHP 首页资料链接：多用户 ID 时安全回退

- 发现原实现无条件将已认证首页的第一个 `userdetails.php?id=...` 链接认作当前账号。首页若同时含有其他用户资料链接，则可能用他人 UID 读取其详情，并错误关联到当前用户做种汇总。新增合成 HTTP 失败回归确认了该风险。
- 现仅在首页资料链接可归一为**唯一一个不同 UID**时沿用原只读资料路径；出现两个不同 UID 或无法确认时回退到当前登录会话的 `usercp.php`，UID 保持未知，不触发以不明 UID 为参数的额外做种 AJAX 请求。同一 UID 在导航中重复出现不会误判为多账号。该约束适用于共用 NexusPHP 适配器的 HDTime 与 HHClub，不改变 M-TEAM API。
- 唯一链接本身**不构成已完成的登录用户身份认证**；仍需以 Synology 实际站点当前账号的页面结构核对。多用户链接下可能缺少部分资料字段，此时按未知展示，不应自动从其他账号推断身份、也不得把合成测试标为线上真实用户统计验收。

## NexusPHP 首页做种链接不得充当用户身份来源

- 在上一轮“首页多个不同 UID 回退”基础上发现新边界：`_user_profile_link` 原先只看 `userdetails.php` 路径和 `id`，会将 `userdetails.php?id=...&action=2` 当前做种链接错误认作普通个人资料候选；只有该链接时可能推断出不属于当前账号的 UID，有其他用户的做种链接时还会错误触发多 UID 回退。

- 修复范围是已知链接用途混淆，不代表只凭首页唯一普通资料链接就已经独立证明登录身份；生产三站点字段核对依旧 `PENDING_EXTERNAL`，未请求 Synology、站点实时接口或真实下载器。
