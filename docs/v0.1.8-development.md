# PackBreaker v0.1.8 研发文档

当前状态：**设计已冻结 / Stage A、Stage B、Stage C、Stage D、Stage E、Stage F、Stage G、Stage H、Stage I 均已完成 / v0.1.8 发布前现场证据已全部通过**

相邻研发基线：`v0.1.7`

版本定位：**产品流程收口 / 任务执行链路重构**

核心原则：**能力不删，独立入口移除；降低用户操作复杂度，不降低现有安全门。**

---

## 1. 版本背景

PackBreaker 当前已经具备扫描、文件识别、拆包、Repair、下载器交互、文件系统操作、Dry Run / Preflight、人工确认、operation journal、对账、保留期清理、日志、恢复与重试等能力。

早期为了研发、调试和真实环境安全验证，产品把：

- 「预演与确认」
- 「清理与对账」

作为相对独立的一级功能展示。

随着任务中心、监控任务和统一安全执行链逐步成熟，这种产品结构开始产生额外复杂度：

1. 普通用户真正关心的是任务是否安全、正确地完成，而不是内部阶段名称。
2. 普通低风险任务不应该每次都要求进入独立预演页面。
3. 监控任务属于无人值守任务，不能依赖用户每次进入 Web 手动确认。
4. 清理、校验与对账本质上属于任务闭环和异常恢复能力，不应要求用户主动理解内部 journal。
5. 一级菜单过多会让 PackBreaker 的使用路径显得比实际需求复杂。

因此 v0.1.8 对产品工作流进行收口。

---

## 2. v0.1.8 核心目标

本版本删除「预演与确认」「清理与对账」两个独立产品入口，将其能力整合进任务生命周期。

用户层工作流由：

```text
扫描
→ 预演与确认
→ 拆包 / Repair
→ 清理与对账
→ 完成
```

收口为：

```text
扫描
→ 风险检查
→ 执行
→ 自动校验
→ 完成
```

系统内部仍保留并加强：

```text
扫描
→ 生成执行计划
→ 风险分析
→ 授权检查
→ 必要时 Web / Telegram 确认
→ 执行文件系统 / 下载器操作
→ 结果校验
→ operation / 状态对账
→ 安全收尾
→ 生成执行结果
→ 完成
```

简化的是交互，不是安全机制。

## 3. 本版本范围

### 3.1 本版本要做

- 删除「预演与确认」独立一级菜单和独立页面。
- 删除「清理与对账」独立一级菜单和独立页面。
- 删除对应旧前端页面路由，不做兼容跳转。
- 将 Execution Plan / Preflight 能力纳入任务详情与统一执行链。
- 引入统一风险检查与授权模型。
- 手动任务高风险操作支持 Web 确认。
- 监控任务支持高风险操作预授权。
- 未授权监控任务进入等待确认，不发生真实副作用。
- v0.1.8 正式实现 Telegram 直接批准 / 拒绝监控任务高风险操作。
- 任务完成后统一展示执行、校验、对账与收尾结果。
- 保留 operation journal 的安全对账、幂等、恢复和 retention purge 能力。
- 统一任务详情、状态文案和日志阶段表达。

### 3.2 本版本不做

- 不删除 Dry Run / Preflight 底层能力。
- 不删除 Execution Gate。
- 不删除 operation journal。
- 不降低文件系统、下载器、Repair 的既有安全不变量。
- 不改变现有拆包核心匹配算法。
- 不改变站点扫描规则。
- 不为了统一流程抹平 qBittorrent / Transmission 的协议差异。
- 不引入新的站点类型。
- 不把 Telegram 审批实现成绕过 Web 安全门的第二套执行器。
- 不把 AI Agent 扩展为任意写操作入口。

## 4. 产品结构调整

### 4.1 删除「预演与确认」独立入口

前端删除：

- 主导航「预演与确认」
- 独立审核中心页面入口
- 总览中的对应快捷入口
- 仅为该一级页面存在的页面切换逻辑

底层 Preflight、Execution Gate、Execution Plan、人工审核证据继续保留。

### 4.2 删除「清理与对账」独立入口

前端删除：

- 主导航「清理与对账」
- 独立维护中心页面
- 总览中的对应快捷入口

底层：

- operation maintenance report
- reconcile
- retention plan
- purge
- rollback / recovery

继续保留，并改为任务详情、异常提示和内部收尾能力使用。

### 4.3 旧 URL

当前项目尚无需要维护兼容性的真实用户，因此旧前端 URL / 页面路由直接删除：

- 不做 Redirect。
- 不保留 deprecated 页面。
- 不增加兼容层。
- 删除前必须全项目清理菜单、按钮、测试、文档和跳转引用。

后端仍被内部安全链使用的 API 不因为页面删除而直接移除；必须先完成调用迁移和无引用证明。

## 5. 统一任务生命周期

v0.1.8 的产品层阶段统一为：

```text
待执行
→ 扫描 / 分析
→ 执行计划
→ 风险检查
→ 等待确认（仅必要时）
→ 执行
→ 自动校验
→ 收尾
→ 完成
```

异常结果：

- 部分成功
- 失败
- 已取消
- 等待人工确认

### 5.1 与现有底层 TaskStatus 的关系

v0.1.8 **不直接用一套新的简化枚举替换现有安全状态机**。

现有底层 `TaskStatus` 包含：

- PENDING
- ANALYZING
- SEARCHING
- MATCHING
- VERIFYING
- PREFLIGHT
- AWAITING_CONFIRMATION
- LINKING
- ADDING
- CLIENT_VERIFYING
- SEEDING
- DONE
- PAUSED
- RETRY
- FAILED
- CANCELLING
- ROLLING_BACK
- CANCELLED

这些状态已经绑定 Execution Gate、journal、副作用恢复和取消 / 回滚语义，Stage B 必须以“统一编排 + UI 投影”的方式收口，不能为追求表面简洁破坏既有状态机。

任务中心的 `TaskExecutionStatus / TaskExecutionPhase` 继续作为长期任务执行记录的聚合视图，后续按统一生命周期重新映射。

## 6. Execution Plan

原「预演」不再作为独立一级功能，而是每次真实执行前的内部执行计划。

执行计划至少需要能表达：

- 发现对象数量
- 匹配 / 忽略数量
- 待拆包对象
- 文件系统动作
- 创建目录 / 链接 / 复制 / 移动等动作
- 删除 / 覆盖类动作
- 下载器动作
- Repair 动作
- 预计下载量 / 校验方式
- 阻断原因
- 是否 current
- 是否 ready
- 是否已经开始副作用
- 风险等级与风险项

普通低风险任务生成计划后可继续自动执行。

Execution Plan 本身不得修改真实文件或下载器状态。

---

## 7. 风险检查

统一引入 Risk Check。

建议产品风险等级：

- 低风险
- 中风险
- 高风险

风险等级是产品展示和授权判断输入，不能绕过现有领域安全门。

### 7.1 默认低风险行为

原则上包括：

- 扫描目录
- 读取 torrent / 下载器 / 站点信息
- 文件存在性检查
- 哈希与验证读取
- 只读对账
- 在既有安全策略允许下创建目录
- 已经过 Execution Gate 证明安全的常规输出动作
- 不涉及不可逆删除 / 覆盖的常规处理

### 7.2 高风险行为

至少包括：

- 删除原始文件
- 批量删除
- 覆盖已有文件
- 强制覆盖
- 跨数据根的大规模移动
- 删除非临时目录
- 可能修改原文件的 Repair
- 删除下载器任务
- 删除下载器任务及文件
- 修改下载器保存目录
- 修改任务文件关联
- 其他可能造成不可逆结果的动作

任何无法证明安全边界的动作都按失败关闭处理。

## 8. 手动任务确认

普通低风险手动任务：

```text
创建任务
→ 扫描 / 分析
→ Execution Plan
→ Risk Check
→ 自动执行
→ 自动校验
→ 完成
```

高风险手动任务：

```text
创建任务
→ 扫描 / 分析
→ Execution Plan
→ Risk Check
→ 等待确认
→ Web 展示真实影响范围
→ 用户批准
→ 再次验证计划 current
→ 正式执行
```

Web 确认弹窗必须展示真实风险项和影响数量，不能只提供笼统“是否继续”。

---

## 9. 监控任务预授权

监控任务属于无人值守任务，因此采用预授权机制。

创建 / 编辑监控任务时允许配置自动执行权限，例如：

```text
☑ 允许常规拆包
☑ 允许安全输出
☑ 允许正常临时收尾

□ 允许删除原文件
□ 允许覆盖已有文件
□ 允许修改下载器任务
□ 允许删除下载器任务
```

高风险授权默认关闭。

已有监控任务从 v0.1.7 升级后不得因为迁移自动扩大权限。

---

## 10. 未授权监控任务

如果某次监控任务的 Execution Plan 包含超出预授权范围的高风险动作：

1. 不进入真实副作用阶段。
2. 任务进入等待人工确认。
3. 持久化当前 run、plan、风险摘要和审批状态。
4. Web 可以批准 / 拒绝。
5. Telegram 发送审批消息。

用户可以：

- 仅批准本次
- 拒绝本次
- Web 中按产品设计选择是否扩大该监控任务以后允许的权限

“以后允许”属于任务配置变更，必须走正常配置写安全链；Telegram 本版本优先保证“批准本次 / 拒绝本次”完整可靠。

## 11. Telegram 高风险审批

v0.1.8 正式实现监控任务高风险操作 Telegram 直接审批。

示例消息：

```text
⚠️ PackBreaker 高风险操作待确认

任务：电影监控拆包
扫描站点：M-Team

本次执行计划：
拆包：8
移动 / 输出：8
删除原文件：8
修改下载器任务：1

风险等级：高

当前未执行任何真实数据修改。
```

Inline Keyboard 至少提供：

```text
[ ✅ 批准本次 ]
[ ❌ 拒绝执行 ]
[ 🔍 查看详情 ]
```

批准后无需进入 Web。

---

## 12. Telegram 审批安全要求

### 12.1 身份校验

审批只能由明确授权的 Telegram Chat ID / User ID 执行，不能依赖用户名。

### 12.2 Approval Token

每个待审批 run 生成唯一审批标识，并至少绑定：

- task_definition_id
- execution_id / run_id
- execution_plan_id
- execution_plan_hash / digest
- risk_summary
- 创建时间
- 当前审批状态

### 12.3 一次性语义

批准或拒绝成功后审批立即进入终态，旧按钮重复点击不得重复触发授权或执行。

### 12.4 Plan 变化

批准后、真正执行前必须重新验证计划仍 current。

如果文件、下载器绑定、路径映射、计划 digest 或其他安全输入变化：

- 原审批失效。
- 不执行。
- 重新生成 / 刷新计划。
- 重新请求审批。

### 12.5 审计

记录：

- 审批来源（Web / Telegram / 预授权）
- 审批主体
- 时间
- approved / rejected / expired
- execution / run
- plan digest

不得记录 Bot Token 等秘密。

### 12.6 重启恢复

Pending approval 必须持久化。

容器重启不能：

- 丢失等待确认状态
- 自动放行
- 重复发送副作用

---

## 13. Telegram 技术约束

Telegram 只负责“表达审批请求 + 改变 authorization 状态”，不能直接调用文件系统或下载器写方法。

统一原则：

```text
Telegram approval
→ Authorization Service
→ 再次验证 Execution Plan / Gate
→ 统一 Task Execution Service
→ journal-backed 副作用
```

不得形成：

```text
Telegram callback
→ 直接删文件 / 改下载器
```

---

## 14. 任务原子性

高风险行为未授权时，默认在副作用阶段前阻断整个 run。

```text
扫描
→ 生成完整执行计划
→ 风险检查
→ 授权检查失败
→ 等待确认
```

在确认前不得发生该 run 的真实业务副作用。

如果已有底层流程存在不可拆分的安全预处理，则 Stage B 必须明确哪些动作属于“只读 / 计划阶段”，哪些动作属于“真实副作用”，不能用产品文案掩盖实际写入。

---

## 15. Dry Run / Preflight 新定位

Dry Run / Preflight 底层能力继续保留。

默认产品体验不再要求所有任务进入独立页面。

高级设置可保留：

```text
□ 每次执行前要求完整 Dry Run / 人工检查
```

适用于：

- 新环境
- 高价值数据
- 新下载器 / 新路径映射
- 调试
- 高风险 Repair
- 真实环境验收

---

## 16. 自动校验、收尾与对账

任务执行后进入统一自动校验 / 收尾阶段。

### 16.1 文件系统

- 目标对象是否存在
- 快照 / inode / 路径等证据是否符合既有规则
- 目标状态是否与计划一致
- 是否存在需要关注的残留

### 16.2 下载器

- 任务身份是否仍一致
- save path / ownership / hash 等证据是否符合对应适配器契约
- 校验 / seeding 状态是否按当前下载器能力收敛

### 16.3 PackBreaker

- Task / TaskExecution 状态
- Execution Plan / Gate 当前性
- operation journal 状态
- receipt / retry / recovery 状态

### 16.4 结果

正常完成时用户只需要看到：

```text
任务执行：完成
文件系统：正常
下载器：正常
异常残留：0
✅ 本次任务已完整闭环
```

底层仍保留足够的技术信息用于日志与排错。

---

## 17. Reconcile 的保留方式

operation reconcile 继续坚持：

> 重新证明，而不是强制修改。

现有安全原则全部保留：

- 只能对可证明的 `RECONCILE_REQUIRED` journal 执行受控 reconcile。
- 缺失 after snapshot 时不得根据“当前路径存在”猜测历史副作用成功。
- 下载器 reconcile 继续按具体协议和已有快照证明。
- HTTP 未知结果继续依赖幂等 receipt 和真实状态重放收敛。

删除的是独立产品页面，不是 reconcile 安全语义。

任务详情保留：

- 重新校验
- 重新对账 / 重新检查
- 查看异常 operation
- 重试失败项

---

## 18. Cleanup 的保留方式

当前“清理”包含两类不同语义，v0.1.8 必须继续区分。

### 18.1 任务收尾

属于当前 run 的安全临时内容 / 状态收尾，由统一任务生命周期自动完成。

### 18.2 Operation retention purge

operation journal retention cleanup 不是普通“删临时文件”。

现有规则继续保留：

- 仅安全终态 journal 进入 retention candidate。
- 必须重新证明任务终态、保留期与零恢复引用。
- purge 保留 tombstone。
- 原幂等键不能因为 payload 清理后重新触发历史副作用。

该能力不再作为一级菜单展示，但不能弱化为普通数据库清理。

---

## 19. 部分成功与异常

如果执行动作完成，但自动校验 / reconcile 发现异常：

- 不能显示完全成功。
- 使用“部分成功 / 需要处理”等明确结果。
- 展示失败阶段和影响对象。

至少记录：

- 失败阶段
- 失败对象
- 失败原因
- 已执行动作
- 未执行动作
- 是否可安全重试

---

## 20. Retry 与幂等

重试原则：

> 只重试可以安全证明需要重试的失败步骤，不重复已完成危险操作。

v0.1.8 必须继续依赖现有：

- Idempotency-Key
- receipt
- operation journal
- before / after snapshot
- checkpoint
- startup recovery

对文件系统、下载器、Repair、Cleanup、Reconcile 和 Telegram Approval 都要求幂等。

Telegram 一次批准最多产生一次有效授权状态变更。

---

## 21. 任务列表与任务详情

### 21.1 任务列表

不再展示“预演状态 / 清理状态 / 对账状态”三个孤立概念。

围绕：

- 任务名称
- 类型
- 扫描站点
- 执行时间
- 当前状态
- 成功数
- 失败数
- 最近执行时间
- 操作

### 21.2 任务详情

按生命周期展示：

```text
扫描 / 分析       ✓
执行计划          ✓
风险检查          ✓
授权              ✓ / 等待中
执行              ✓
自动校验          ✓
收尾 / 对账       ✓
```

同时展示：

- Execution Plan 摘要
- 风险项
- 审批来源和审批状态
- 执行结果
- 自动校验结果
- operation 异常
- 可安全重试 / 重新检查动作

## 23. 后端架构目标

Stage B 之后的统一编排目标：

```text
scan / analyze
→ build_execution_plan
→ check_risk
→ check_authorization
→ request_approval (必要时)
→ execute
→ verify
→ reconcile
→ cleanup / finalize
```

这不是要求把现有所有服务重写成一个巨型 Service，而是要求形成一个明确的 orchestrator / lifecycle coordinator。

既有：

- TaskAnalysisService
- Execution Gate / Plan
- TaskLinking / Adding / ClientVerification / Seeding
- TaskOperationService
- TaskRecovery / TaskDriver
- TaskDefinitionExecutionService

应优先复用和编排，避免重复实现。

## 24. 数据模型方向

正式实现时至少需要稳定表达：

### 24.1 Risk Summary

## 27. 安全原则

### 27.1 无法证明安全就不执行

```text
无法确认是否安全
=
不执行高风险操作
```

### 27.2 Plan 与 Execute 分离

Execution Plan / Risk Check 不得偷偷产生真实副作用。

### 27.3 高风险必须有明确授权来源

只能来自：

- 当前 Web 明确确认
- 当前 Telegram 明确审批
- 已持久化并仍有效的监控任务预授权

### 27.4 Telegram 不是执行器

Telegram 只改变授权状态。

### 27.5 不破坏既有安全不变量

源数据只读、路径失败关闭、journal intent-before-effect、快照证明、幂等恢复、下载器协议差异等 AGENTS.md 规则全部继续生效。

Stage F 可以直接删除独立入口，但 `PreflightReviewCenter` 中仍有价值的证据展示 / 人工确认 UI 需要先迁入任务详情，不能先删组件后丢能力。

### 32.2 前端「清理与对账」

当前实现位置：

- `frontend/src/App.vue`
  - 一级导航注册「清理与对账」。
- `frontend/src/components/Management.vue`
  - 独立维护页面读取 maintenance report。
- `frontend/src/components/OperationalOverview.vue`
  - 总览展示需要关注的 operation 数量，并跳转到该页面。
- `frontend/src/components/TaskOperationCenter.vue`
  - 任务级 operation 已经具备“重新检查 / 对账”的安全动作。

结论：全局一级维护页面可以删除，但 `TaskOperationCenter` 这类任务级安全动作应保留并整合进任务详情。

### 32.3 Cleanup 后端实际边界

当前 `TaskOperationService.maintenance_report()` 把两类内容汇总到同一个维护视图：

- `RECONCILE_REQUIRED / ROLLBACK_BLOCKED`：需要关注 / 修复。
- `NOOP / ROLLED_BACK`：可能进入 retention cleanup。

`retention_plan()` 会检查保留期和引用关系；`purge_retained()` 使用幂等 receipt，并保留 tombstone。

因此 v0.1.8 的“自动清理”不能简单等价为自动调用 purge：

- 任务运行时临时内容收尾可以自动化。
- operation journal retention purge 继续保持独立安全语义和严格证明。

### 32.4 Reconcile 后端实际边界

`TaskOperationService.reconcile()` 已经是严格的 journal 重新证明链：

- 新 reconcile 只接受 `RECONCILE_REQUIRED`。
- 文件系统缺 after snapshot 时拒绝猜测。
- 下载器 / Repair 通过对应 binding 与真实状态重新证明。
- 使用 Idempotency-Key / receipt 处理重放。

Stage E 应复用这一能力，不新建“自动强制修复”接口。

### 32.5 手动任务当前流程

`TaskDefinitionExecutionService.materialize_manual()` 当前职责是：

1. 校验手动任务、站点和来源可运行。
2. 创建 `TaskExecution`。
3. 将来源对象物化为既有底层 `UnpackTask`。
4. 执行记录最终进入 `PENDING / WAITING`，等待后续安全链。

Service 注释已经明确：

> 把长期任务的来源快照物化为既有 UnpackTask；不越过预演/人工确认安全门。

同时 `create_execution_plan()` 已经可以针对 execution item 调用现有 TaskAnalysisService 生成 Execution Plan。

结论：Stage B 应把“物化 → 分析 / Plan → 授权 → Execute”串成统一生命周期，而不是重写安全 Run。

### 32.6 监控任务当前流程

当前：

- `TaskDefinitionDriver` 查找到期监控任务。
- `TaskDefinitionExecutionService.scan_monitor()` 处理 Cron / 立即扫描。
- 有 overlap policy、watermark、debounce、stability detection、目录分页等逻辑。
- 发现 ready 对象后创建 `TaskExecution` 并物化底层 `UnpackTask`。

这套发现 / 去重 / 稳定性逻辑已经成熟，应保持。

Stage B/C 主要在“物化之后”统一 Plan、Risk、Authorization、Execute；不要把 monitor discovery 重写进新的风险模块。

### 32.7 两层状态模型

当前存在两层状态：

1. 底层 `TaskStatus`：安全执行状态机，绑定分析、审核、Execution Gate、LINKING、ADDING、客户端下载器验证、SEEDING、取消与回滚。
2. `TaskExecutionStatus / TaskExecutionPhase`：任务中心长期执行记录的聚合展示。

`reconcile_task_execution()` 会把底层 UnpackTask 当前 `TaskStatus` 投影回 TaskExecution item，再聚合 execution 状态。

结论：

- v0.1.8 不新增第三套互相竞争的状态机。
- Stage B 首先定义统一 lifecycle 的“阶段投影”，复用现有 TaskStatus 作为真实安全状态。
- Approval 可能需要新增持久化领域状态，但不能与 `AWAITING_CONFIRMATION` 含义冲突。

### 32.8 Telegram 当前能力

现有 Telegram 有两条能力：

1. 普通通知 Provider：`TelegramNotificationProvider`，只负责 `sendMessage`。
2. Telegram AI：`TelegramAIClient + AITelegramDriver + AITelegramService`。

Telegram AI 已经具备：

- getUpdates long polling
- 持久化 last_update_id cursor
- Chat ID / User ID allowlist
- proxy 复用
- 单条消息异常隔离
- rate limit

但当前 `allowed_updates` **只请求 `message`**。

当前 `TelegramInboundUpdate` 只解析：

- update_id
- message_id
- chat_id
- user_id
- text

当前未实现：

- `callback_query`
- Inline Keyboard `reply_markup`
- `answerCallbackQuery`
- callback data 协议
- Approval 领域状态

因此 Stage D 需要扩展现有 Telegram client / polling 基础设施，而不是新建第二套 Bot Token 和 polling driver。

### 32.9 Stage B 推荐重构入口

优先入口：

1. `TaskDefinitionExecutionService`
   - 继续负责 manual / monitor 的来源物化。
   - 增加或委托统一 run lifecycle coordinator。
2. `TaskAnalysisService`
   - 继续作为现有 Execution Plan / Gate 能力来源。
3. `TaskActionService` 与 TaskLinking / Adding / ClientVerification / Seeding
   - 继续作为副作用执行主链。
4. `TaskOperationService`
   - 继续提供 journal reconcile / retention 安全能力。
5. 新增薄的 Lifecycle / Authorization 层
   - 编排 plan、risk、approval 和 execute。
   - 不复制文件系统 / 下载器写逻辑。

Stage B 第一批代码改动建议先解决：

- lifecycle 数据结构 / 阶段投影；
- 一个 execution item 如何从 WAITING 自动推进到已有 Execution Plan；
- 低风险如何自动授权；
- 高风险如何停在明确的 waiting-for-approval 边界；
- 保证此时仍为零副作用。

Telegram Approval 放到 Stage D，不在 Stage B 提前耦合 Bot 逻辑。
