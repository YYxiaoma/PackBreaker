## 四、正式发布前必须完成的外部门禁

1. **冻结受审提交**：完整核对候选工作树中的源代码、测试、文档、OpenAPI 和 lockfiles 后，在明确授权下提交并推送 `candidate/v1.1.0`。正式版绝不能直接从当前未提交工作树创建 Tag。
2. **候选 GitHub Actions CI**：验证 AMD64、原生 ARM64 的完整测试、双架构 Docker 构建与启动、数据库迁移/备份恢复、真实 Docker qBittorrent/Transmission 合成 API 链路；审阅具体 run/job 结果。
3. **相邻版本与 updater**：以 `v1.0.15` 官方不可变 digest 为基线，在隔离 Docker 卷内完成 `v1.0.15 → v1.1.0 候选 → 恢复升级前备份、回滚 v1.0.15`，并验证 Web updater 的成功与失败回滚。不可在 NAS 生产配置中做这些破坏性模拟。
4. **候选镜像交付决策**：现有 `candidate-v1015-image-delivery.yml` 固定 `1.0.15`，不能用于发布 `1.1.0`；如需在 GHCR/Docker Hub 交付独立候选，应先建立经审查、绑定精确 `1.1.0` commit SHA 的非正式候选流程，拒绝覆盖已有候选及推进 `stable/latest`。
5. **正式发布授权**：只有独立门禁和候选镜像摘要证据齐全、用户批准后才可以合并正式主线、创建 `v1.1.0` Tag，并由正式 Release workflow 建立双架构不可变镜像、SBOM、Release Manifest、SHA256SUMS 与发布资产回读，最后经系统门禁推进版本通道。

本次 WebCodex Runner 无可执行 Docker 命令（本地 `docker version` 未启动），因此 **Docker 镜像、原生 ARM64、跨版本升级回滚及发布资产**在本次审查中均未声称通过。

## 五、行为及风险约束

- 对已存在的目标文件，`VERIFY_REUSE_OR_STOP` 仅在同 inode 或完整 SHA-256 一致、源/目标快照冻结且落位前再次校验时才允许复用；若内容不符、软链接或快照漂移，则保持失败关闭。已有文件的复用 Journal 不代表该文件由本次任务创建，因此**不得将其视为允许自动删除/清理的 ownership 证明**。
- 不允许通过重试绕过 `RECONCILE_REQUIRED`、缺失 Journal、外部 Torrent 归属不符或客户端校验失败；遇到任何未知副作用须停下对账。
- NAS 生产容器及其媒体目录未进行升级/迁移/清理；生产部署必须独立备份 `/config`、保存原镜像不可变 digest，检查既有下载器映射和 `PUID/PGID` 后才按正式流程操作。
- **当前结论**：源码/单影片验收适合进入候选分支提交与 CI 阶段，尚不具备直接创建正式 Tag、推送生产 `latest` 或升级 NAS 的证据。
