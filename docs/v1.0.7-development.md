# PackBreaker v1.0.7 研发设计：影片去重

## 1. 版本目标

v1.0.7 新增“影片去重”能力，并补强 v1.0.6 在线升级在浏览器刷新后的状态恢复。

影片去重解决两个影视目录中存在完全相同影片文件时的重复占用问题。用户明确指定保留目录 A 与去重目录 B；PackBreaker 只把 A 视为权威来源，只对 B 执行替换。

最终自动替换的安全前提固定为：

1. A/B 都是稳定普通文件；
2. 文件大小一致；
3. 候选元数据与快速指纹用于缩小匹配范围；
4. 完整 SHA-256 必须一致；
5. 执行前重新确认文件快照未变化；
6. 所有危险写操作必须进入持久化 journal，并可在崩溃后恢复或 fail closed。

宁可漏掉重复文件，也不能误删非重复文件。

## 2. 产品命名与入口

- 功能名称统一为“影片去重”，不再使用“大包去重”。
- 入口位于“任务中心”，不增加新的一级导航。
- v1.0.7 首版以手动任务为主，不引入 Cron 自动去重。

## 3. 创建任务

字段：

- 任务名称：用户填写；
- 保留目录 A：权威源目录；
- 去重目录 B：待释放重复占用的目录；
- 去重方式：AUTO（默认）、HARDLINK、SYMLINK、SCAN_ONLY；
- AUTO 跨文件系统策略：STOP（默认）或用户显式允许 SYMLINK；
- 包含子目录：默认开启；
- 最小文件大小；
- 视频扩展名：复用现有默认配置。

自动模式禁止静默降级。用户没有明确允许软链接 fallback 时，硬链接不可用只能提示并跳过或阻断。

## 4. 链接语义

硬链接要求 A 文件与 B 目标父目录位于同一文件系统，并且实际 hardlink probe 成功。物理磁盘是否相同不是充分条件，判断以文件系统设备身份与实际 link 能力为准。

软链接允许跨文件系统，但 B 会依赖 A 的路径。A 被删除、移动或挂载路径变化后，B 会失效；读取 B 的其它 Docker 容器也必须通过兼容挂载访问 A。UI 必须明确提示这种依赖关系。

v1.0.7 首版不支持 reflink/copy 作为去重模式。

## 5. 重复判定

判定分层进行：

1. 文件名/路径解析：标题、年份、版本、分辨率、片源、编码、制作组；
2. 文件大小；
3. 固定采样区的快速 SHA-256 指纹；
4. 完整文件 SHA-256。

只有完整 SHA-256 一致的候选才允许进入自动替换。元数据无法完整识别但完整 SHA-256 一致时，标记“内容重复但元数据不足”，默认要求人工确认。

完整 hash 按 device/inode/size/mtime_ns/ctime_ns 缓存，避免同一源 inode 被重复读取。

## 6. 文件稳定性

扫描、Hash 与执行前后均记录和校验 device、inode、size、mtime_ns、ctime_ns、link_count、mode、uid、gid。任一关键身份发生变化，返回 SOURCE_CHANGED 或 TARGET_CHANGED，禁止继续执行旧计划。

临时文件、下载中的文件、symlink、非普通文件默认不进入自动替换。

## 7. 预计释放空间

UI 同时展示“重复逻辑大小”和“预计可释放空间”。B 原 inode 的 link_count 大于 1 时，替换一个目录项未必释放数据块，因此该项目预计释放空间按 0 处理。实际空间可能受稀疏文件、压缩、快照和文件系统实现影响，始终标注为“预计”。

## 8. 安全替换

严禁先删除 B 再创建 link，因为进程在两步之间崩溃会导致 B 路径消失。

硬链接替换扩展 SafeFilesystemGateway：

1. 在 B 同一父目录创建 deterministic 临时硬链接，指向 A；
2. 校验临时链接与 A 的 device/inode 一致；
3. 使用 Linux renameat2(RENAME_EXCHANGE) 原子交换临时路径与 B；
4. 再次确认 B 已指向 A；
5. journal 提交后安全 unlink 临时路径上的旧 B inode。

软链接同样先在 B 父目录创建 deterministic 临时 symlink，验证目标路径，再通过原子交换替换 B，绝不先删除 B。

## 9. 崩溃恢复

每个替换 pair 独立 journal。推荐阶段：INTENT_RECORDED、TEMP_LINK_CREATED、EXCHANGED、VERIFIED、COMMITTED、FAILED、RECOVERY_REQUIRED。

恢复时只根据 journal ownership、operation token 与文件快照判断现场。无法证明归属时禁止 unlink/overwrite，进入 RECOVERY_REQUIRED。

## 10. 持久化模型

新增独立影片去重模型，不伪造 downloader/torrent 身份：

- dedup_job：任务配置、状态、阶段、cursor、统计；
- dedup_file_inventory：A/B 文件清单、快照、媒体元数据、指纹与 hash；
- dedup_pair：候选关系、验证结论、最终动作、预计释放空间；
- dedup_operation_journal：危险替换的幂等操作记录与 before/after snapshot。

现有 operation_journal 外键强绑定 unpack_task，v1.0.7 不为了影片去重扩大重构范围。

## 11. 大目录扫描

禁止一次性加载整个目录树。采用有界批次、持久 cursor、inventory 落库和容器重启续扫。Hash 只针对候选文件，禁止对整个媒体库无差别计算完整 SHA-256。

## 12. 任务状态

状态包括：PENDING、SCANNING、MATCHING、VERIFYING、REVIEW_REQUIRED、EXECUTING、FINAL_VERIFYING、COMPLETED、PARTIAL_FAILED、FAILED、CANCELLED、RECOVERY_REQUIRED。

页面刷新、关闭浏览器、重新登录都不得停止后台任务。

## 13. UI

任务中心增加“影片去重”视图。结果至少展示影片、A/B 路径、分辨率、制作组、文件大小、metadata/size/quick hash/full SHA-256 匹配结论、最终执行方式、预计释放空间、状态与错误码。

详情同时展示 A/B device、inode、link count、mtime、SHA-256。

## 14. 在线升级刷新连续性修复

v1.0.6 的一次性 updater 在接管后独立于浏览器运行，刷新页面不会中止已接管升级；但前端 pendingIdempotencyKey / targetInFlight 当前只存在内存中，刷新后可能丢失“成功后自动 reload”关联。

v1.0.7 调整：

1. helper_status 是升级状态的唯一事实来源；
2. 页面重新加载后，从 GET /system/upgrade 恢复 active phase 与目标版本；
3. 未确认 POST 请求的 Idempotency-Key 与目标写入 sessionStorage，刷新后复用；
4. phase 为 succeeded 且 current_version 等于 helper target_version 时，根据 helper request_id 自动刷新；
5. 将已完成自动刷新的 request id 写入 sessionStorage，防止 reload loop。

## 15. 测试与验收

至少覆盖同 size 不同内容、full SHA-256 相同、已是同 inode、不同文件系统、用户允许/不允许 symlink fallback、文件在验证期间发生变化、target 原 link_count 大于 1、临时链接冲突、原子交换前后崩溃、重复 Idempotency-Key、浏览器刷新恢复，以及在线升级各活动阶段刷新恢复与成功后只自动 reload 一次。

正式验收时必须证明成功硬链接 pair 满足 inode(A) == inode(B)，不能只比较内容相同。

## 16. 隔离真实文件系统验收

运行镜像内提供 `backend.app.movie_dedup_acceptance`，开发仓库同时提供薄包装 `scripts/check_movie_dedup_e2e.py`。两者都会在真实 Linux 文件系统上创建小型合成媒体 fixture，直接调用影片去重领域服务验证链接语义；不会扫描指定父目录内已有媒体，只会使用名称以 `packbreaker-movie-dedup-acceptance-` 开头的临时目录，并在退出时清理。

脚本要求同时指定 `--live` 与 `--acknowledge-synthetic-file-writes`，避免误操作。NAS 容器验收示例：

```bash
docker exec packbreaker python -m backend.app.movie_dedup_acceptance \
  --data-root /data \
  --source-parent /data/downloads \
  --target-parent /data/downloads2 \
  --live \
  --acknowledge-synthetic-file-writes
```

开发工作区也可以直接运行：

```bash
python scripts/check_movie_dedup_e2e.py \
  --data-root /workspace/PackBreaker \
  --source-parent /workspace/PackBreaker \
  --target-parent /workspace/PackBreaker \
  --live \
  --acknowledge-synthetic-file-writes
```

当前工作区已取得两组真实文件系统证据：

1. 同一文件系统：AUTO + STOP 解析为 HARDLINK；执行完成后 A/B `st_ino` 相同，operation journal 为 `COMMITTED`，临时旧 B 已清理；
2. 不同文件系统：AUTO + STOP 返回 `CROSS_DEVICE_BLOCKED` 且 B inode 不变；显式允许 SYMLINK 后完成原子软链接替换并可读取相同内容；
3. 同大小但内容不同的负例：完整内容验证不一致，B inode 保持不变；
4. 所有合成 fixture 在验收结束后自动清理。

### 16.2 2026-10-02 Synology NAS 真实数据库隔离迁移/回滚

随后使用生产容器创建的一致性 SQLite 备份，在完全隔离的 `/config` 副本上执行相邻版本迁移/回滚验收。现场首先确认生产容器实际版本为 **v1.0.4**，备份 manifest 为：

- app version：`1.0.4`
- Alembic revision：`0031_site_type_capacity_v101`
- backup SHA-256：`78adbe68eaabdadef023be98cc90787fe2ae120467885d101c0e1284e6f2ef06`

验收路径与结果：

1. 使用正式 v1.0.6 不可变镜像验证并恢复该 v1.0.4 真实备份，恢复结果迁移到 `0032_cookiecloud_v105`；
2. 隔离启动 v1.0.6，确认 `baseline_version=1.0.6`、`baseline_revision=0032_cookiecloud_v105`；
3. 使用同一隔离数据库副本启动 v1.0.7 candidate，确认直接迁移到 `candidate_version=1.0.7`、`candidate_revision=0033_movie_dedup_v107`；
4. 使用原始备份恢复，再次启动 v1.0.6，确认 `rollback_version=1.0.6`、`rollback_revision=0032_cookiecloud_v105`；
5. 全流程未停止生产 PackBreaker 容器，未向隔离容器挂载真实媒体目录。

该验收证明了“真实 v1.0.4 数据库内容经 v1.0.6 再升级 v1.0.7”的迁移链与 v1.0.6 回滚备份路径可用。由于当前生产实际仍是 v1.0.4，正式发布前还需补一项直接 `v1.0.4 -> v1.0.7 candidate -> v1.0.4` 隔离验证，以覆盖真实生产升级路径，不应把本节结果解释为生产当前版本为 v1.0.6。

在线升级的真实容器替换验收仍要求 Docker daemon 与 `/var/run/docker.sock`。当前 WebCodex 工作区没有 Docker socket，因此这里只能证明前端刷新连续性、helper 状态恢复单元/浏览器门禁，不能把 Docker 现场升级描述为已完成。
